## 2. 바꾸지 않는 것

- 기획서의 바꾸지 않는 원칙 (원본은 Postgres, 판은 추가만, 비공개 기본, 위험한 동작은 결재 뒤 실행)
- API와 worker 프로세스는 LLM을 부르지 않는다. AI 일은 러너가 맡고, 러너는 `runner` 프로필로 서버의 별도 컨테이너에서도 돈다
- 네 계층: 진입 → 응용 → 도메인 ← 저장
- 모듈 = 스키마, 모듈 사이 외래키 없음
- 마이그레이션(SQL)이 표의 원본이다
- `ReviewPolicy`, `ChangeOp`, 엔티티의 판단 메서드, 테스트는 줄이는 대상이 아니다

## 3. 목표 구조

컨셉은 **입구는 여러 개, 문은 하나, 공통은 선언, 예외만 코드**다.

```text
진입   CairnApp + REST · MCP · worker · 명령줄 어댑터
         ↓ Actor
응용   Operation (Command · Read)      공통 규칙은 기반 클래스의 run 한 곳
         ↓
도메인 Entity · Policy · Actor         판단만
         ↓
저장   TableRepository · Gateway · Outbox
```

### 패턴

| 패턴 | 위치 | 고른 이유 |
|---|---|---|
| Command | 쓰기 행위 | 결재 뒤 실행, 감사, 재시도, 입구 생성이 모두 "요청을 객체로" 다뤄야 된다. `ChangeOp`로 이미 검증했다 |
| Template Method | `Operation.run` | 단계가 고정이라 가장 단순하다 |
| Adapter | 입구 | 프로토콜 지식을 입구에 가둔다 |
| Strategy | `ReviewRule`, `Access` | 규칙이 교체되는 곳이다 |
| Repository | `TableRepository` | 진행 중인 구조를 쓴다 |
| Outbox + Observer | 모듈 사이 후속 일 | 이미 동작한다 |

쓰지 않는 것:

- **별도 Kernel, Bus:** 기반 클래스가 같은 일을 한다
- **Chain of Responsibility:** 단계가 동적으로 바뀌어야 할 요구가 없다
- **Service Locator, 전역 변경 상태:** 동시 요청이 섞인다 (시험 확인). Actor는 인자로 넘긴다
- **직접 만든 쿼리 빌더:** ORM을 쓴다
- **Event Sourcing, 마이크로서비스:** 필요 없다

### ORM

**ORM을 넣는다** (2026-11-02 사용자 결정). 지금 코드에는 ORM이 없고 `postgres` 드라이버만 있다.
기획서의 2026-10-10 "ORM 없음"과 2026-11-02 "Drizzle을 고르지 않음" 결정을 뒤집으므로 결정 기록을 함께 고친다.
아래는 객체설계 10장 순서의 제안이고, 라이브러리 승인 전에는 넣지 않는다.

| 항목 | 내용 |
|---|---|
| 겪은 문제 | 손으로 쓴 `INSERT` 55곳, `SELECT` 117개, 행 변환 반복, SQL의 칼럼 오타를 컴파일러가 못 잡음 |
| 후보 | Drizzle `0.45.4`. 같은 `postgres` 드라이버 위에서 돌고 런타임 의존성이 없다 |
| 들어갈 자리 | 미리 만든 쿼리 템플릿 `QueryTemplate`(2026-11-08 사용자 결정). 쿼리 빌더로 모양만 만들어 한 번 SQL 글자로 바꿔 두고, 실행은 그때의 연결에서 `postgres`로. `TableRepository`의 `load` · `lock`과 표 하나의 읽기에서 사용 |
| 표의 원본 | 마이그레이션 유지. `db-rows.mjs`를 넓혀 Drizzle 표(`<모듈>.schema.ts`)를 함께 생성한다 |
| 비용 | 패키지 하나, 단순 조회 1회당 약 0.34ms 증가, 내부 동작에 기대는 감싸기 |
| 고치는 범위 | 저장 계층부터. 기존 `sql`과 한 트랜잭션에서 함께 쓸 수 있어 묶음별로 옮긴다 |
| 빼는 방법 | 저장과 선언형 읽기는 기반 클래스 안의 호출만 되돌린다. `fetch()`에서 ORM을 쓰는 읽기 40곳은 SQL로 다시 쓴다. 모듈은 `drizzle-orm`을 직접 가져오지 않고 `platform/base`가 다시 내보낸 것만 쓴다 |

**2026-11-02 시험 결과** (저장소 밖, 임시 DB, 표 61개 · 칼럼 519개). 최신 마이그레이션은 표 63개 · 칼럼 534개라 1단계를 시작할 때 다시 돌린다:

| 시험 | 결과 | 결정 |
|---|---|---|
| `drizzle-kit pull` | 빈 문자열 기본값 15곳이 깨져 구문 오류 43개. `bytea`, `vector` 미지원 | 쓰지 않는다. `drizzle-kit`도 넣지 않는다 |
| `db-rows.mjs` 방식 생성 | 표 61개 컴파일 성공, `CHECK`의 enum 45칸, 날짜 `Date`, 없는 칸과 값은 컴파일 오류 | 이 방식을 쓴다 |
| 클라이언트를 그대로 넘김 | 기존 `sql`의 날짜가 문자열로 바뀜 | 금지 |
| 트랜잭션 객체를 그대로 넘김 | `options`가 없어 실패 | 감싸기로 해결 |
| `options`만 가린 감싸기 | 기존 `sql`의 날짜 유지, 커밋과 롤백이 둘 다 함께 동작 | 2026-11-08 템플릿으로 대체 (내부 동작에 기대지 않음) |
| 기본 `jsonb()` + 감싸기 | 값이 이중 인코딩되어 DB에 문자열로 저장됨 | 생성기가 전용 `jsonb` 칸을 만든다 |
| 전용 `jsonb` 칸 | 양쪽으로 읽고 써도 객체 유지 | 채택 |
| `pg_bigm` + 조인 | `sql` 조각으로 실행됨 | 채택 |
| 속도 | 단순 조회 3,000회: `sql` 959ms, ORM 1,983ms | 뜨거운 경로는 SQL 유지 가능 |

**2026-11-08 시험 결과** (저장소 밖, 임시 DB, 단순 조회 3,000번):

| 방법 | 트랜잭션 안 | 시간 | 결정 |
|---|---|---|---|
| 지금 `sql` | 됨 | 600ms | 표를 잇거나 모으는 읽기에 남김 |
| Drizzle 매번 만들기 | 됨 | 1,615ms | 쓰지 않는다 |
| Drizzle `prepare` | **밖에서 돎** (만든 순간의 연결을 붙잡음, 소스 `PostgresJsPreparedQuery.client`) | 490ms | 쓰지 않는다 |
| `drizzle({ client })` | | | 만드는 순간 우리 연결의 날짜 파서를 바꿔 문자열이 됨 (소스 `postgres-js/driver.js`). 쓰지 않는다 |
| 미리 만든 템플릿 (`toSQL` 한 번 + 그때의 연결로 `unsafe`) | 됨 (커밋 전 행이 보이고 롤백되면 사라짐) | 520ms | **채택** |

같은 시험에서: 행 모양(Date · bigint → number · 배열 · jsonb · 불리언)이 지금 `sql`과 같고, 빠진 값은 이름과 함께 오류, `FOR UPDATE SKIP LOCKED`가 된다.
`inArray`에 자리(placeholder)를 넣으면 `in $2`가 되어 구문 오류라 `= ANY(자리)`를 쓴다. Drizzle은 고른 칸을 자기 쪽에서 이름에 맞춰 주므로, 우리처럼 SQL을 바로 돌리면 고른 칸의 이름이 DB 칸 이름과 같아야 한다 (템플릿이 만들 때 검사).

쓰기 공통화는 이미 `TableRepository`가 ORM 없이 한다. ORM의 이득은 읽기와 조건을 칼럼 타입으로 검사하는 데 있다.
감싸기는 Drizzle 내부에 기대므로 버전을 고정하고, 날짜, `jsonb`, bigint, 배열, bytea 왕복을 테스트로 지킨다.
표 인터페이스(`<모듈>.tables.ts`)는 지금처럼 import 없이 두고, Drizzle 표는 `<모듈>.schema.ts`로 따로 생성해 이 파일만 라이브러리 경계 검사의 예외로 둔다.
`.view.ts`가 표 인터페이스를 가져오므로, 합치면 Drizzle이 웹 타입 검사까지 들어가기 때문이다.

Prisma는 자체 스키마가 원본이 되어 고르지 않는다. TypeORM은 데코레이터 엔티티가 `TableEntity`와 겹친다.
Kysely는 타입 생성과 잘 맞지만 ORM이 아니라 쿼리 빌더다. Drizzle이 막힐 때의 대안이다.

### 레이어별 객체

| 계층 | 지금 | 목표 |
|---|---|---|
| 진입 | `*.api.ts`, `*.controller.ts`, `*.tool.ts`, Response | `CairnApp`, 공통 어댑터, `Authenticator`, View. 프로토콜 경로만 Controller로 남긴다 |
| 응용 | Service, Query, Input | `Operation` → `Command`, `Read`. Input은 유지 |
| 도메인 | Entity, Policy, Actor | `TableEntity`, Policy, Actor. Actor에 `requestId`, `now` 추가 |
| 저장 | Repository, Gateway | ORM 기반 `TableRepository`, Gateway, Outbox |

Context 역할은 새 클래스 대신 Actor가 맡는다. 이미 모든 Service와 Query의 첫 인자다.
객체설계 9장의 "Actor는 종류·id·공간·권한만 가진다"를 "요청 하나의 값(`requestId`, `now`)까지"로 고친다. 작업 토큰에 싣는 값은 지금처럼 종류·id·공간·권한뿐이다.

```text
Operation<I, O>                 name, access, input, limit
├ Read<I, O>                    visibility, fetch()
└ Command<I, O>                 once, risk, perform()
    ├ Create<E, I>              build()
    ├ Change<E, I>              apply()
    └ Remove<E, I>
```

```ts
export class PauseAgent extends AgentChange<VersionInput> {
  readonly access = Access.owner;
  readonly input = VersionInput;

  protected apply(agent: Agent): void {
    agent.pause();
  }
}

// agent.api.ts (REST 어댑터). 경로는 입구에만 둔다
Route.post('api/agents/:id/pause', PauseAgent);
```

`access`는 필수라 빠뜨리면 컴파일이 실패한다. 하위 클래스는 세 곳 이상 쓰일 때만 만든다.
이름을 `Action`으로 하지 않는 이유는 플러그인의 `BaseAction`과 겹치기 때문이다.

손으로 남기는 것:

- 프로토콜 경로 31개 (OAuth, 로그인, 설치, MCP, SSE, 파일). 안에서 Operation을 부른다
- 복잡한 쓰기. `ChangeService`의 로직은 Command의 `perform`으로 옮기고 `ReviewPolicy`는 그대로 둔다
- 복잡한 읽기. SELECT 117개 중 77개(66%)는 선언과 ORM으로, 40개는 `fetch()`에서 ORM과 SQL 조각으로 쓴다. `pg_bigm` 검색과 `LATERAL` 집계가 여기 든다

## 4. 공통 규칙의 자리

| 규칙 | 자리 | 이유 |
|---|---|---|
| 본문 크기, 보안 머리글 | HTTP 어댑터 | 바이트 단계이고 HTTP에만 의미 있다 |
| 쿠키 출처 확인 | HTTP 어댑터 | 쿠키에만 의미 있다 |
| 신원 확인 | `Authenticator` | 자격 증명은 달라도 결과는 Actor 하나다 |
| 접근 권한 | `Operation.access` | 누락을 컴파일 오류로 막는다 |
| 입력 검사 | `Operation.input` | 채널이 달라도 같은 검사를 한다 |
| 속도 제한 | `Operation.limit` | 손으로 쓰는 3곳을 선언으로 바꾼다 |
| 중복 방지 | `Command.once(열쇠)` | 손으로 쓰는 9개 파일을 선언으로 바꾼다. 열쇠 주인이 요청자·러너·작업·기기·공간·결재로 6가지이고 3곳은 없을 수도 있어 열쇠를 함수로 받는다 |
| 민감정보 제거 | `Command`의 입력 처리 | 판이 되기 전에 막는다 |
| 결재 | `Command.risk` | 승인 뒤 같은 Command를 실행한다 |
| 트랜잭션 | `Command` | 쓰기 규칙을 한 곳에 둔다 |
| 시간 제한 | DB 연결 | 잠금 대기로 연결이 묶이는 것을 막는다 |
| 감사 기록, 추적 id | `Operation.run` | 누락할 수 없게 한다 |
| 행 단위 권한 | `Read.visibility`, Entity | 데이터를 봐야 판단할 수 있다 |
| 오류 모양 | 어댑터 | 같은 `DomainError`를 프로토콜에 맞게 바꾼다 |

공통 규칙은 같은 권한을 뜻하지 않는다. 소재 읽기는 REST에서 주인만, MCP에서 `write` 권한으로 의도적으로 다르다.
같은 문을 지나되 권한은 행위마다 선언한다. 작업 토큰을 REST에서 막는 규칙도 유지한다.

## 5. worker 정책

할 일이 없으면 DB를 조회하지 않는다. "아무 일도 없는데 미래에 할 의무가 있는가"로 깨어날 조건을 정한다.
기획서 2026-11-01의 "30초 조회는 안전망으로 남긴다" 결정을 뒤집으므로 결정 기록을 함께 고친다.

| 의무 | 지금 | 목표 |
|---|---|---|
| 새 이벤트 | NOTIFY | 유지 |
| 시작과 재연결 | 한 번 처리 | 유지 |
| 재시도 | 30초 조회 | `next_attempt_at` 마감 타이머 |
| 빌린 뒤 죽은 이벤트 | 30초 조회 | 시작 복구 + 같은 마감 타이머 |
| 작업 임대 만료 | 30초 Job | `lease_until` 마감 타이머 |
| LISTEN 끊김 | 드라이버가 실패를 삼킴 | 전용 연결로 감지하고 재시도 |
| GitHub 동기화 | 5분 Job | 외부 연동 예외로 유지 |


## 6. 문자열과 설정

옮길 대상은 **로직 안의 문자열**이다. 분기, 비교, 이벤트 발행, 권한 판단에 쓰이는 값이다.

| 값 | 원본 | 쓰는 법 |
|---|---|---|
| 상태, 종류, 공개 범위 | DB `CHECK` 제약 62개 | `pnpm db:rows`가 `as const` 객체와 타입 생성 |
| 칼럼 이름 | 마이그레이션 | 표 인터페이스 키로 검사 |
| 이벤트 이름 | `events.json` | `keyof`로 검사, 경계 검사가 발행자와 구독자 확인 |
| 작업 종류, 스킬, 필요 권한 | `task-kinds.json` | `Task.SKILLS`, `SCOPES` 대체 |
| 재시도, 임대, 속도 제한 | `policy.json` | 시작할 때 읽음 |
| 사용자 문구 | `messages.ko.json` | 타입이 있는 키로 참조 |
| 비밀값, 주소 | 환경 변수 | 지금 그대로 |

TypeScript `enum`은 쓰지 않는다. DB가 돌려주는 일반 문자열과 맞추려면 형 변환이 계속 필요하다.

남기는 문자열: SQL 본문, 도구 설명, 경로 선언, `S256` 같은 프로토콜 값, `sha256` 같은 라이브러리 인자, CSS 클래스.
숫자 상수 100개도 전부 옮기지 않는다. `TITLE_MAX` 같은 도메인 규칙은 코드에 남긴다.

## 7. 모듈 경계

모듈은 다른 모듈의 코드와 표를 모른다. 허용하는 길은 둘이다.

```text
쓰기와 후속 일   이벤트 (outbox)
동기 읽기        platform의 등록소
                 vault:  lookups.provide('wiki.visible', 구현)
                 blog:   lookups.ask('wiki.visible', actor, ids)
```

동기 읽기는 `wiki.visible`, `session.note` 둘뿐이다. 그래서 `contracts` 폴더와 Port 체계는 만들지 않는다.
등록은 `ArchiveQuery.register`와 같은 방식이다. `modules.json`에는 제공과 사용을 적어 검사한다.

| 메뉴 | 모듈 | 상태 |
|---|---|---|
| 운영 | `task` | 일치 |
| 지식 | `vault` | 일치 |
| 블로그 | `blog` | 일치 |
| 설정 | `account` | 일치 |
| 연결 | `account`, `task/ai`, `platform/plugin` | 흩어짐, 11장 |

`mcp`는 도메인이 아니라 입구다. 메뉴와 맞출 대상이 아니다.
여러 모듈을 함께 보여 주는 조합은 화면의 일이다. 결재 화면이 글과 작업 API를 함께 부르는 것은 그대로 둔다.

### 기능 패키지

새 콘솔 메뉴나 블로그 같은 호스팅 기능은 코어를 고치지 않고 **기능 패키지**로 더한다.

```text
plugins/<이름>/
  cairn-plugin.json     메뉴, 경로, 권한, 스키마 선언
  migrations/           자기 스키마에만
  server/               Command, Read
  web/                  콘솔 화면, 공개 화면
```

- **표:** 패키지마다 전용 스키마를 가진다. 코어 표에 SQL을 쓰거나 외래키를 걸지 않는다
- **공통으로 쓰는 것:** 인증, 권한, 파일, outbox, `TableEntity`, `Operation`
- **입구:** 패키지는 서버를 다시 시작하지 않고 켜지므로, API와 MCP 도구는 Nest Controller가 아니라 목록 파일의 경로와 `cairn`에 등록한 `Operation`으로 연다
- **검사:** `pnpm check`가 자기 스키마만 쓰는지 확인한다
- **적용:** 쓸 권한과 표 변경을 주인이 승인한 뒤 배포하고 켠다
- **실행 중인 에이전트:** 표나 서버 코드를 스스로 바꾸지 않는다. 서버 코드는 비밀값과 비공개 세션에 닿기 때문이다
- **다른 사람의 플러그인:** 이 길을 쓰지 않는다. 별도 서버 + 웹훅 방식으로 나중에 정한다

고르지 않은 방향:

- **범용 표** (`records(kind, data jsonb)`): 외래키, 제약, 인덱스, 타입을 잃는다
- **비슷한 표 합치기:** `session_revisions`와 `wiki_revisions`는 15칸 중 11칸이 같지만, 합치면 모듈 경계와 트리거가 약해진다. 반복은 표가 아니라 기반 클래스에서 없앤다

Paperclip의 `plugin-llm-wiki`가 같은 방식이다. 전용 DB 스키마, 마이그레이션, 메뉴와 페이지를 목록 파일에 선언한다.

### 단계별 주의

- **1단계:** `db-rows.mjs`가 Drizzle 표(`<모듈>.schema.ts`)를 만들고 `QueryTemplate`을 더한다 (enum 값은 4단계). 날짜, `jsonb`, bigint, 배열, bytea 왕복 테스트부터 넣고, 최신 스키마로 시험을 다시 돌린다. ORM의 이득은 읽기에 있으므로 저장이 아니라 읽기로 잰다. 4단계의 enum 생성도 이 작업과 같은 생성기를 쓴다.
- **2단계:** `database.ts`가 진행 중인 작업과 겹친다. 30초 조회를 지우기 전에 듣기 복구를 먼저 넣는다.
- **3단계:** 글 초안의 민감정보 제거는 vault 안의 `SensitivePolicy`를 쓴다. 자리는 11장에서 정한다. `lock_timeout`은 복원처럼 오래 걸리는 작업에서 풀어야 한다. `request_approval.note`는 지금 통과하는 값을 막지 않게 8,000자로 맞춘다.
- **4단계:** 값의 이름만 바뀌므로 동작은 같아야 한다.
- **7단계:** 판단 기준은 줄 수, 테스트 변경량, 읽기 쉬움이다. 나쁘면 확대하지 않는다.
- **8단계:** 전환 순서는 `task`, `blog`, `vault`, `account`다. 마지막에 Nest를 뺄지 판단한다.
- **11단계:** 미리 만들지 않는다. 첫 새 기능을 만들 때 그 기능에 필요한 확장 지점부터 제안한다. 플러그인 화면은 웹 빌드에 묶여 있어 패키지를 더하면 재빌드가 필요하다.

## 13. 1단계 결과 (2026-11-08 끝남)

미리 만든 쿼리 템플릿(`QueryTemplate`)으로 표 하나의 읽기를 옮겼다. 결정은 기획서 결정 기록(2026-11-08), 규칙은 객체설계 6 · 10장, 시험은 3장.

| 커밋 | 내용 |
|---|---|
| `bb7017f` | 기반: `drizzle-orm@0.45.4`(고정), `QueryTemplate`(`of` · `choose` · `byId` · `anyOf`), `TableRepository`의 한 줄 읽기 · 잠그기, `pnpm db:rows`가 `<모듈>.schema.ts`도 생성, 경계 검사, 묶음 생성기 |

| `fef6012` · `3c2e362` · `c526793` · `c1c0b81` · `1b42928` | platform · task · blog · vault · account의 표 하나의 읽기를 템플릿으로 |

### 템플릿으로 옮기지 않은 읽기 (SQL로 둔다)

- 표를 잇거나(JOIN · LATERAL) 모으는(count · sum · `jsonb_agg`) 읽기, 재귀, pg_bigm 검색
- JSON 경로(`payload->>'tool'`), 칸 별칭(`*, post_id AS id`), 실행 때 정하는 표(`NodeRepository`)
- DB 시계(`now()`)로 거르는데 부르는 쪽이 시각을 넘기지 않는 읽기 (`isLive`, `findBySession`): 시각의 출처를 바꾸지 않았다
- 상수를 SQL에 그대로 써야 부분 색인을 쓰는 조건은 칸 자체를 조건으로 쓴다 (`heartbeats_due_idx WHERE enabled`)

### 기반에 더할 후보 (같은 문제가 여러 곳에서 나왔다)

- `TableRepository.save`가 `saved()` 뒤에 `saveParts`를 불러 바뀐 칸 기록이 지워진다 (`Post.relinked`로 비켜 감)
- ON CONFLICT를 붙이는 INSERT (`AuthorizationCode` · `PluginState`), version이 없는 표의 저장 (`users` · `plugins`), `id`가 아닌 열쇠로 잠그기 (`lockLiveByName` · `lockByRefresh`, vault의 `node_id`)
- 딸린 표만 바뀌어도 version을 올리는 저장: 세 곳이 `unsaved`를 덮어쓴다 (`Space` · `Device`, 행 잠금이 목적인 `Owner`)
- `f.columns`의 필수 칸 오류 문구, 0부터 받는 정수 읽기
- 쓰기에도 템플릿을 쓸지: 저장은 `TableRepository`가 이미 공통이라 지금은 이득이 없다
