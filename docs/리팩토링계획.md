# Cairn 리팩토링 계획

> 진행 중인 리팩토링과 남은 일. 0 · 1 · 11단계는 끝났고 다음은 2단계(worker 정책)다 (13장). 상태: **제안**. 단계마다 인터페이스를 승인받은 뒤 구현한다.
> 숫자는 계획을 쓴 때의 코드(`19bec85` · `1b5d948`)에서 주석과 빈 줄, 테스트를 뺀 서버 모듈 코드로 쟀다.
> 규칙의 원본은 [기획서](기획서.md), [객체 설계](객체설계.md), [테이블 설계](테이블설계.md), [API 설계](API설계.md)다.
> 단계가 끝나면 확정된 내용을 그 문서로 옮기고 여기서 지운다.

## 1. 왜 고치는가

| 문제 | 측정 | 결과 |
|---|---|---|
| 코드 양 | `api` · `tool`의 반복 토큰 75% 이상 | 판단 로직보다 배선이 길다 |
| 공통 규칙 | 권한 표현 5가지, 중복 방지 9개 파일, 속도 제한 3개 Service | 기계가 검사할 수 없다 |
| 요청 추적 | 요청 로그, 추적 id, 시간 제한 없음 | 장애 원인을 따라가기 어렵다 |
| 쉬는 동안의 일 | worker 조회와 임대 확인이 각각 30초마다 | 할 일이 없어도 DB를 부른다 |
| 듣기 복구 | DB 포트가 닫혔다 열리면 `sql.listen`이 복구되지 않음 (시험 확인) | 30초 조회가 버그를 가리고 있다 |
| 문자열 | 로직의 비교 문자열 서버 117, 웹 228, 러너 27 | 오타를 컴파일러가 잡지 못한다 |
| 모듈 결합 | `blog → vault` import 4건, 이벤트 이름을 문자열로 공유 | 원칙 4와 코드가 어긋난다 |
| 민감정보 | 글 초안에 비밀값 제거 없음 | 판은 고칠 수 없어 들어가면 지우기 어렵다 |

권한: `actor`를 받는데 본문에 확인이 보이지 않는 66곳을 모두 읽었고(2026-11-09), 빠진 확인은 없었다.
권한이 빠진 것이 아니라 의도가 선언되지 않아 기계가 검사할 수 없다는 점이 문제다. 찾은 약한 곳 7개는 3단계에서 고쳤다 (기획서 결정 기록 2026-11-09).

## 2. 바꾸지 않는 것

- 기획서의 바꾸지 않는 원칙 (원본은 Postgres, 판은 추가만, 비공개 기본, 위험한 동작은 결재 뒤 실행)
- API와 worker 프로세스는 LLM을 부르지 않는다. AI 일은 러너가 맡고, 러너는 서버와 함께 뜨는 별도 컨테이너(서버 러너)에서도 돈다
- 네 계층: 진입 → 응용 → 도메인 ← 저장
- 모듈 = 스키마, 모듈 사이 외래키 없음
- 마이그레이션(SQL)이 표의 원본이다
- `ReviewPolicy`, `ChangeOp`, 엔티티의 판단 메서드, 테스트는 줄이는 대상이 아니다

## 3. 목표 구조

컨셉은 **입구는 여러 개, 문은 하나, 공통은 선언, 예외만 코드**다.

```text
진입   CairnApp + REST · MCP · worker · 명령줄 어댑터
         ↓ Actor
응용   Operation (Command · Read)      공통 규칙은 기반 클래스의 run 한 곳
         ↓
도메인 Entity · Policy · Actor         판단만
         ↓
저장   TableRepository · Gateway · Outbox
```

### 패턴

| 패턴 | 위치 | 고른 이유 |
|---|---|---|
| Command | 쓰기 행위 | 결재 뒤 실행, 감사, 재시도, 입구 생성이 모두 "요청을 객체로" 다뤄야 된다. `ChangeOp`로 이미 검증했다 |
| Template Method | `Operation.run` | 단계가 고정이라 가장 단순하다 |
| Adapter | 입구 | 프로토콜 지식을 입구에 가둔다 |
| Strategy | `ReviewRule`, `Access` | 규칙이 교체되는 곳이다 |
| Repository | `TableRepository` | 지금 구조를 쓴다 |
| Outbox + Observer | 모듈 사이 후속 일 | 이미 동작한다 |

쓰지 않는 것:

- **별도 Kernel, Bus:** 기반 클래스가 같은 일을 한다
- **Chain of Responsibility:** 단계가 동적으로 바뀌어야 할 요구가 없다
- **Service Locator, 전역 변경 상태:** 동시 요청이 섞인다 (시험 확인). Actor는 인자로 넘긴다
- **Event Sourcing, 마이크로서비스:** 필요 없다

### ORM

Drizzle(`0.45.4` 고정)은 생성된 표(이름 · 칸 · 행 타입)로만 쓰고, 표 하나의 읽기 · 쓰기는 코어의 조건 규칙(`TableQuery`)이 SQL을 만든다. 표를 잇거나 모으는 쿼리는 각 모듈의 SQL이다.
결정은 기획서 결정 기록(2026-11-08), 규칙은 객체설계 6 · 10장.

- 표 인터페이스(`<모듈>.tables.ts`)는 import 없이 두고, Drizzle 표는 `<모듈>.schema.ts`로 따로 생성해 이 파일만 라이브러리 경계 검사의 예외로 둔다. `.view.ts`가 표 인터페이스를 가져오므로, 합치면 Drizzle이 웹 타입 검사까지 들어간다.
- `drizzle-kit`은 넣지 않는다. `drizzle-kit pull`은 빈 문자열 기본값에서 구문 오류를 내고 `bytea` · `vector`를 지원하지 않는다 (2026-11-02 시험). 표는 `pnpm db:rows`가 만든다.
- Drizzle이 막힐 때의 대안은 Kysely다 (타입 생성과 잘 맞는 쿼리 빌더). Prisma는 자체 스키마가 원본이 되고, TypeORM은 데코레이터 엔티티가 `TableEntity`와 겹쳐 고르지 않는다.

### 레이어별 객체

| 계층 | 지금 | 목표 |
|---|---|---|
| 진입 | `*.api.ts`, `*.controller.ts`, `*.tool.ts`, View | `CairnApp`, 공통 어댑터, `Authenticator`, View. 프로토콜 경로만 Controller로 남긴다 |
| 응용 | Service, Query, Input | `Operation` → `Command`, `Read`. Input은 유지 |
| 도메인 | `TableEntity`, Policy, Actor | 그대로. Actor에 `requestId`, `now` 추가 |
| 저장 | `TableRepository`(조건 규칙), Gateway, Outbox | 그대로 |

Context 역할은 새 클래스 대신 Actor가 맡는다. 이미 모든 Service와 Query의 첫 인자다.
객체설계 9장의 "Actor는 종류·id·공간·권한만 가진다"를 "요청 하나의 값(`requestId`, `now`)까지"로 고친다. 작업 토큰에 싣는 값은 지금처럼 종류·id·공간·권한뿐이다.

```text
Operation<I, O>                 name, access, input, limit
├ Read<I, O>                    visibility, fetch()
└ Command<I, O>                 once, risk, perform()
    ├ Create<E, I>              build()
    ├ Change<E, I>              apply()
    └ Remove<E, I>
```

```ts
export class PauseAgent extends AgentChange<VersionInput> {
  readonly access = Access.owner;
  readonly input = VersionInput;

  protected apply(agent: Agent): void {
    agent.pause();
  }
}

// agent.api.ts (REST 어댑터). 경로는 입구에만 둔다
Route.post('api/agents/:id/pause', PauseAgent);
```

`access`는 필수라 빠뜨리면 컴파일이 실패한다. 하위 클래스는 세 곳 이상 쓰일 때만 만든다.
이름을 `Action`으로 하지 않는 이유는 플러그인의 `BaseAction`과 겹치기 때문이다.
`Operation`은 기능 패키지에서 먼저 쓴다 (`platform/base/operation.ts`, 객체설계 12장). 7단계에서 코어로 넓힌다.

손으로 남기는 것:

- 프로토콜 경로 31개 (OAuth, 로그인, 설치, MCP, SSE, 파일). 안에서 Operation을 부른다
- 복잡한 쓰기. `ChangeService`의 로직은 Command의 `perform`으로 옮기고 `ReviewPolicy`는 그대로 둔다
- 복잡한 읽기. 표를 잇거나 모으는 읽기는 `fetch()`에서 그 모듈의 SQL로 쓴다 (객체설계 6장). `pg_bigm` 검색과 `LATERAL` 집계가 여기 든다

## 4. 공통 규칙의 자리

| 규칙 | 자리 | 이유 |
|---|---|---|
| 본문 크기, 보안 머리글 | HTTP 어댑터 | 바이트 단계이고 HTTP에만 의미 있다 |
| 쿠키 출처 확인 | HTTP 어댑터 | 쿠키에만 의미 있다 |
| 신원 확인 | `Authenticator` | 자격 증명은 달라도 결과는 Actor 하나다 |
| 접근 권한 | `Operation.access` | 누락을 컴파일 오류로 막는다 |
| 입력 검사 | `Operation.input` | 채널이 달라도 같은 검사를 한다 |
| 속도 제한 | `Operation.limit` | 손으로 쓰는 3곳을 선언으로 바꾼다 |
| 중복 방지 | `Command.once(열쇠)` | 손으로 쓰는 9개 파일을 선언으로 바꾼다. 열쇠 주인이 요청자·러너·작업·기기·공간·결재로 6가지이고 3곳은 없을 수도 있어 열쇠를 함수로 받는다 |
| 민감정보 제거 | `Command`의 입력 처리 | 판이 되기 전에 막는다 |
| 결재 | `Command.risk` | 승인 뒤 같은 Command를 실행한다 |
| 트랜잭션 | `Command` | 쓰기 규칙을 한 곳에 둔다 |
| 시간 제한 | DB 연결 | 잠금 대기로 연결이 묶이는 것을 막는다 |
| 감사 기록, 추적 id | `Operation.run` | 누락할 수 없게 한다 |
| 행 단위 권한 | `Read.visibility`, Entity | 데이터를 봐야 판단할 수 있다 |
| 오류 모양 | 어댑터 | 같은 `DomainError`를 프로토콜에 맞게 바꾼다 |

공통 규칙은 같은 권한을 뜻하지 않는다. 소재 읽기는 REST에서 주인만, MCP에서 `write` 권한으로 의도적으로 다르다.
같은 문을 지나되 권한은 행위마다 선언한다. 작업 토큰을 REST에서 막는 규칙도 유지한다.

## 5. worker 정책

할 일이 없으면 DB를 조회하지 않는다. "아무 일도 없는데 미래에 할 의무가 있는가"로 깨어날 조건을 정한다.
기획서 2026-11-01의 "30초 조회는 안전망으로 남긴다" 결정을 뒤집으므로 결정 기록을 함께 고친다.

| 의무 | 지금 | 목표 |
|---|---|---|
| 새 이벤트 | NOTIFY | 유지 |
| 시작과 재연결 | 한 번 처리 | 유지 |
| 재시도 | 30초 조회 | `next_attempt_at` 마감 타이머 |
| 빌린 뒤 죽은 이벤트 | 30초 조회 | 시작 복구 + 같은 마감 타이머 |
| 작업 임대 만료 | 30초 Job | `lease_until` 마감 타이머 |
| LISTEN 끊김 | 드라이버가 실패를 삼킴 | 전용 연결로 감지하고 재시도 |
| GitHub 동기화 | 5분 Job | 외부 연동 예외로 유지 |

```ts
// platform/base/database.ts
export class Listener {
  readonly ready: Promise<void>;
  stop(): Promise<void>;
}
listen(channel, onMessage, onReady?): Listener;

// platform/worker/work-scheduler.ts
export class WorkScheduler {
  // setTimeout 한도(약 24.8일)를 넘는 시각은 한도에서 깨어나 다시 잰다
  at(key: string, when: Date | null, run: () => void): void;
  stop(): void;
}

// platform/base/base-due-job.ts
export abstract class BaseDueJob {
  abstract readonly name: string;
  abstract run(): Promise<Date | null>;
}

// platform/worker/core-workers.ts
due(job: BaseDueJob, ...wakeTopics: string[]): void;
```

```text
drain():
    비울 때까지 tick()
    next = SELECT min(coalesce(next_attempt_at, now()))
           WHERE processed_at IS NULL AND failed_at IS NULL
    scheduler.at('outbox', next, wake)
```

Paperclip에서 가져오는 것은 "쉬는 동안 조회하지 않고 실제 마감에 깨어난다"는 원칙과 단일 마감 스케줄러다.
수십 개 큐를 위한 조정기는 가져오지 않는다. 신호도 프로세스 내부가 아니라 NOTIFY를 쓴다. Cairn은 `server`와 `worker`가 나뉘어 있기 때문이다.

## 6. 문자열과 설정

옮길 대상은 **로직 안의 문자열**이다. 분기, 비교, 이벤트 발행, 권한 판단에 쓰이는 값이다.

| 값 | 원본 | 쓰는 법 |
|---|---|---|
| 상태, 종류, 공개 범위 | DB `CHECK` 제약 62개 | `pnpm db:rows`가 `as const` 객체와 타입 생성 |
| 칼럼 이름 | 마이그레이션 | 표 인터페이스 키로 검사 |
| 이벤트 이름 | `events.json` | `keyof`로 검사, 경계 검사가 발행자와 구독자 확인 |
| 작업 종류, 스킬, 필요 권한 | `task-kinds.json` | `Task.SKILLS`, `SCOPES` 대체 |
| 재시도, 임대, 속도 제한 | `policy.json` | 시작할 때 읽음 |
| 사용자 문구 | `messages.ko.json` | 타입이 있는 키로 참조 |
| 비밀값, 주소 | 환경 변수 | 지금 그대로 |

TypeScript `enum`은 쓰지 않는다. DB가 돌려주는 일반 문자열과 맞추려면 형 변환이 계속 필요하다.

남기는 문자열: SQL 본문, 경로 선언, `S256` 같은 프로토콜 값, `sha256` 같은 라이브러리 인자, CSS 클래스.
**AI가 읽는 글은 코드 밖에 둔다 (2026-11-14, 바뀜)**: 도구 설명 · 입력 칸 설명은 `<모듈>.tools.ko.json`, 러너의 지시문은 러너 스킬 `cairn-runner`의 틀. 저장소 파일이 기본이고 콘솔에서 판을 쌓아 고친다 ([서브 나](서브나.md) 1-0). 처음에 "도구 설명은 남긴다"고 정한 것은 입력 모양과 함께 바뀐다고 봐서였는데, 실제로는 설명이 모양보다 훨씬 자주 바뀌고(AI의 행동을 다듬는 글), 플러그인은 처음부터 목록 파일에 두어 코어와 어긋났다.
숫자 상수 100개도 전부 옮기지 않는다. `TITLE_MAX` 같은 도메인 규칙은 코드에 남긴다.

## 7. 모듈 경계

모듈은 다른 모듈의 코드와 표를 모른다. 허용하는 길은 둘이다.

```text
쓰기와 후속 일   이벤트 (outbox)
동기 읽기        platform의 등록소
                 vault:  lookups.provide('wiki.visible', 구현)
                 blog:   lookups.ask('wiki.visible', actor, ids)
```

동기 읽기는 `wiki.visible`, `session.note` 둘뿐이다. 그래서 `contracts` 폴더와 Port 체계는 만들지 않는다.
등록은 `ArchiveQuery.register`와 같은 방식이다. `modules.json`에는 제공과 사용을 적어 검사한다.

| 메뉴 | 모듈 | 상태 |
|---|---|---|
| 운영 | `task` | 일치 |
| 지식 | `vault` | 일치 |
| 블로그 | `blog` | 일치 |
| 설정 | `account` | 일치 |
| 연결 | `account`, `task/ai`, `platform/plugin` | 흩어짐, 11장 |

`mcp`는 도메인이 아니라 입구다. 메뉴와 맞출 대상이 아니다.
여러 모듈을 함께 보여 주는 조합은 화면의 일이다. 결재 화면이 글과 작업 API를 함께 부르는 것은 그대로 둔다.

### 기능 패키지

새 콘솔 메뉴나 블로그 같은 호스팅 기능은 코어를 고치지 않고 **기능 패키지**로 더한다. 패키지는 자기 스키마만 쓰고, 코어 표에 SQL을 쓰거나 외래키를 걸지 않는다. 구조 · 확장 지점 · 경계는 객체설계 12장.

- **적용:** 쓸 권한과 표 변경을 주인이 승인한 뒤 배포하고 켠다
- **실행 중인 에이전트:** 표나 서버 코드를 스스로 바꾸지 않는다. 서버 코드는 비밀값과 비공개 세션에 닿기 때문이다
- **다른 사람의 플러그인:** 이 길을 쓰지 않는다. 별도 서버 + 웹훅 방식으로 나중에 정한다

고르지 않은 방향:

- **범용 표** (`records(kind, data jsonb)`): 외래키, 제약, 인덱스, 타입을 잃는다
- **비슷한 표 합치기:** `session_revisions`와 `wiki_revisions`는 15칸 중 11칸이 같지만, 합치면 모듈 경계와 트리거가 약해진다. 반복은 표가 아니라 기반 클래스에서 없앤다

---

## 8. 단계

0단계(표 구조), 1단계(ORM: 생성된 표와 코어의 조건 규칙), 3단계(보안 빈틈), 11단계(기능 패키지)는 끝났다. 남은 단계:

| 단계 | 내용 | 끝 기준 | 선행 |
|---|---|---|---|
| 2 | worker 정책 | 쉬는 동안 조회 0, 재연결 복구 테스트 통과 | 0 |
| 4 | enum 생성 | 비교 문자열이 enum으로, `db:check` 통과 | 1 |
| 5 | 설정 파일과 모듈 경계 | `events.json`, `task-kinds.json`, `blog → vault` 0건 | 4 |
| 6 | `CairnApp`, 요청 로그, 추적 id | 시작 코드 한 곳, 모든 요청에 추적 id | 0 |
| 7 | `Operation` 시범 | `task/agent` 전환, 측정 보고 | 1, 6 |
| 8 | `Operation`과 ORM 확대 | 묶음별 전환, `Read`의 공개 범위 필수화 | 7의 판단 |
| 9 | 결재 통합 | 공개가 Command 재실행으로 동작 | 8 |
| 10 | 문구 시범 | 서버 오류 문구 이전, 웹 확대 여부 판단 | 8 |

단계는 하나씩 진행하고, 앞 단계가 커밋된 뒤 다음 단계를 시작한다.

### 단계별 주의

- **2단계:** 30초 조회를 지우기 전에 듣기 복구를 먼저 넣는다.
- **4단계:** 값의 이름만 바뀌므로 동작은 같아야 한다.
- **7단계:** 판단 기준은 줄 수, 테스트 변경량, 읽기 쉬움이다. 나쁘면 확대하지 않는다.
- **8단계:** 전환 순서는 `task`, `blog`, `vault`, `account`다. 마지막에 Nest를 뺄지 판단한다.

## 9. 예상 효과

| 항목 | 값 | 근거 |
|---|---|---|
| `task/agent` | 108줄 → 약 50줄 | 예시 코드 실측, 컴파일 안 함 |
| `blog/basket` | 190줄 → 약 53줄 | 예시 코드 실측, 컴파일 안 함 |
| 진입·응용 전체 | 순감 약 1,400~2,200줄 | 위 두 묶음에서 넓힌 추정, 상한에 가까움 |
| 쉬는 동안 worker 조회 | 하루 약 5,760번 → 0 | 30초 조회 두 개 기준 |

`task/agent`, `blog/basket` 같은 쉬운 폴더의 감축률은 전체보다 2~3배 크다. 넓힌 추정은 7단계 실측으로 다시 잡는다.
단계가 끝날 때마다 실측으로 이 표를 고친다.

## 10. 위험

| 위험 | 대응 |
|---|---|
| 응용 계층 전환이 커짐 | `task/agent`에서 멈출 수 있게 나눈다. 옛 방식과 함께 둘 수 있다 |
| worker가 깨어나지 않음 | DB 재시작 시험을 자동 테스트로 둔다 |
| 끊어진 줄 모르는 TCP 연결 | 쉬는 동안에는 재시도 타이머가 없어 keep-alive가 감지할 때까지 새 이벤트가 늦는다. 최대 지연을 재시작 시험으로 재서 적는다 |
| ORM이 복잡한 쿼리를 가림 | 쿼리 로그로 실제 SQL을 보고, 복잡한 읽기는 SQL 조각을 쓴다 |
| 기반 클래스가 만능이 됨 | 맞지 않는 행위는 옵션을 더하지 않고 직접 구현한다 |
| 생성된 코드 신뢰 | `db:check`가 DB와 생성 파일의 차이를 잡는다 |
| 문구 이전의 가독성 저하 | 서버 오류 문구로 시범 후 판단한다 |

### 기반에 더할 후보 (같은 문제가 또 나오면 더한다)

- `TableRepository.save`가 `saved()` 뒤에 `saveParts`를 불러 바뀐 칸 기록이 지워진다 (`Post.relinked`로 비켜 감)
- ON CONFLICT를 붙이는 INSERT (`AuthorizationCode` · `PluginState`), version이 없는 표의 저장 (`users` · `plugins`), `id`가 아닌 열쇠로 잠그기 (`lockLiveByName` · `lockByRefresh`, vault의 `node_id`)
- 딸린 표만 바뀌어도 version을 올리는 저장: 세 곳이 `unsaved`를 덮어쓴다 (`Space` · `Device`, 행 잠금이 목적인 `Owner`)
- `f.columns`의 필수 칸 오류 문구, 0부터 받는 정수 읽기

조건 규칙 밖에 둔 표 하나의 쿼리 (객체설계 6장의 "패키지(모듈)의 쿼리" 말고):

| 까닭 | SQL로 둔 곳 |
|---|---|
| 쓰는 값의 배열이 `readonly`면 타입이 맞지 않는다 (Drizzle은 `string[]`, 표 인터페이스는 `readonly string[]`) | `session_revisions` · `oauth_clients` · `oauth_tokens` 넣기 |
| OR 조건이 없다 | 주소 겹침 찾기, 쓸 수 있는 AI 로그인 |
| `<> ALL(목록)`, `IS DISTINCT FROM`이 없다 | 글의 참고 wiki, 다른 로그인 끝내기 |
| 칸 자체를 조건으로 쓰지 못한다 (`WHERE enabled`) | 스케줄 (부분 색인 `schedules_due_idx`) |
| 기반 클래스가 아닌 곳은 규칙을 쓰지 못한다 | 복원 저장소, outbox 일꾼 |
| 칸 별칭(`*, post_id AS id`), 실행 때 정하는 표 | 별칭을 쓰는 읽기, `NodeRepository` |
| DB 시계(`now()`)로 거르는데 부르는 쪽이 시각을 넘기지 않는다: 옮기면 시각의 출처가 바뀐다 | `isLive`, `findBySession` |
