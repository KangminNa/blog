# Cairn 코드 작업 병렬 실행

에이전트가 저장소의 코드를 고치는 일(`code`)을 여러 개 동시에 돌려 PR까지 만들고, 머지는 결재 뒤에 한다.
상태는 **4단계까지 구현**이다 (2026-11-10, 8장의 단계 순서로 만든다. 4단계는 가짜 GitHub로 시험했고 진짜 저장소 확인은 남았다). 결정의 이유는 [기획서](기획서.md) 결정 기록(2026-11-10),
러너의 다른 일은 [객체설계](객체설계.md) 13장, 기능 패키지의 틀은 객체설계 12장. 처음 제안과 ORCA 검토는 Claude Docs의 설계 제안서에 있다.

## 1. 하는 일

| 일 | 흐름 | 남는 것 |
|---|---|---|
| 코드 작업 하나 | 저장소 · 고칠 경로 · 지시로 맡김 → 빈 칸이 빌림 → clone · 고치기 · 테스트 → PR → 결재 → 머지 | PR, 실행 기록, 결재 |
| 큰 일 나누기 | 팀장 에이전트가 경로 단위로 나눠 위임 → 칸 수만큼 동시에 → 다 끝나면 팀장이 모음 | 하위 작업마다 PR |

## 2. 원칙

- **셸은 샌드박스 컨테이너(코드 러너 칸) 안에서만 준다.** 내 컴퓨터 러너와 서버 러너는 지금처럼 셸이 없다 (2026-11-01 결정의 예외).
- **칸 하나에 작업 하나.** 칸 수가 곧 병렬 수다. 작업마다 새로 clone하고 끝나면 지운다.
- **에이전트는 브랜치까지만.** push와 PR은 러너(믿는 코드)가 AI가 끝난 뒤에 한다. GitHub 토큰은 에이전트에게 가지 않는다.
- **main에는 결재 뒤에만.** 결재 동작 `code.pr.merge` (원칙 7). main에는 브랜치 보호를 건다.
- **비공개 지식과 코드 작업은 섞지 않는다.** 권한 `code`는 `read_all` · `write`와 함께 줄 수 없다 (`browse`와 같은 이유).
- **바깥은 허용 목록으로만.** 칸은 내부 네트워크에만 있고, 나가는 프록시를 거쳐 허용한 호스트(git, 패키지 저장소)에만 닿는다.
- **서버 본체에는 여전히 AI가 없다** (원칙 6). 서버는 일을 나누고 빌려 주고 결재만 한다.

## 3. 구성

```
 주인(콘솔) ──① 일 맡기기──▶ ┌ Cairn 서버 (AI 없음) ─────────────┐
     ▲                        │ 대기열 · 위임: 경로가 겹치면 기다림 │
     └──⑤ 결재 알림────────── │ 결재: code.pr.merge (주인만)        │
                              │ 기능 패키지 code-github             │
                              └──────────▲─────────────────────────┘
                                         │ ② 빌리기 · ④ 결재 요청 (MCP)
 ┌ 코드 러너 칸 (code-runner-1 · 2) ─────┴─────┐      ┌ 나가는 프록시 ┐      GitHub
 │ 칸 1: 러너 + AI CLI(셸) + 저장소 clone      │──③──▶│ 허용 목록만   │──▶  저장소 · PR
 │ 칸 2: 다른 일 하나를 동시에                 │      └───────────────┘
 └─────────────────────────────────────────────┘
 ⑥ 머지: 첫 버전은 주인이 GitHub에서 직접 하고 승인, 뒤에는 승인하면 서버가 머지
```

- 칸 = 컨테이너 하나. 미리 N개를 띄우고 작업마다 비운다. Docker 소켓은 주지 않는다 (2026-11-06과 같은 이유).
- 칸의 러너는 서버 러너처럼 연결 값으로 스스로 붙되, 칸마다 기기 하나(`코드 러너 <칸>`)를 받는다. 연결 값과 볼륨은 서버 러너와 따로다.
- 칸인지는 서버가 기기로 정한다 (기기 권한 `sandbox`). 러너가 "나는 칸"이라고 알리는 값은 믿지 않는다: 내 컴퓨터 러너가 그렇게 말해도 셸 있는 일을 받지 못한다.

## 4. 흐름

1. 주인(또는 팀장 에이전트의 위임)이 저장소 · 고칠 경로(`paths`) · 지시로 일을 맡긴다.
2. 빈 칸의 러너가 `next_jobs`로 일을 빌린다 (서버는 칸 기기에게만 code를 준다). 같은 저장소에서 경로가 겹치는 일이 돌고 있으면 기다린다.
3. 러너가 얕은 clone → `cairn/<작업>` 브랜치 → 저장소의 `setup`을 하고 AI CLI를 셸과 함께 띄운다.
   AI가 끝나면 러너가 범위 확인 → `checks` → push → PR(draft)을 한다.
4. 러너가 PR을 `code_pull_opened`로 남기고, 결과물을 올린 뒤 작업 토큰으로 `code.pr.merge` 결재를 올린다. 작업은 기다린다.
5. 주인에게 결재가 간다. "고쳐 달라"면 그 말과 함께 같은 에이전트가 다시 한다: 이미 올린 `cairn/<작업>` 브랜치에서 이어서 고치고, 같은 PR이 갱신되며 판(PR의 version)이 올라 새 결재가 올라온다.
6. 주인이 GitHub에서 PR을 머지한 뒤 승인하면, 결재한 판이 지금 PR과 같을 때 패키지가 머지로 남기고 작업이 끝난다 (다르면 실패). 서버가 머지하는 것은 6단계.

## 5. 데이터와 입구

**코어 (task · account)**

| 무엇 | 바뀜 |
|---|---|
| 일의 종류 | `code`. `Task.SCOPES`: `code` → `[code]`. 칸에서만 도는 일은 `Task.SANDBOXED`. 스킬(`Task.SKILLS`: `code` → `cairn-code`)은 3단계, 위임(`Task.DELEGABLE`)은 5단계 |
| 에이전트 권한 | `code`. `read_all` · `write`와 함께 줄 수 없음 (`Agent` 규칙 + 마이그레이션 CHECK) |
| `next_jobs` | 입력은 그대로. 칸 기기(`Actor.inSandbox`)는 `SANDBOXED`만, 다른 러너는 `SANDBOXED`가 아닌 일만 받는다 (`lockNext`) |
| 기기 권한 | `sandbox`: 칸 기기만. 칸으로 연결할 때만 생기고 주인이 줄 수 없다. 칸 기기의 권한은 `run` · `sandbox`로 정해져 있다 (DB CHECK `devices_sandbox_only`) |
| 빌리기 충돌 막기 | `lockNext`가 같은 저장소에서 `paths`가 겹치는(접두어) 달리는 작업이 있으면 건너뛴다 |
| 칸 연결 | `POST /api/devices/code-runner { secret, slot }` (칸 번호 1~99). 칸마다 기기 하나(`코드 러너 <칸>`). 연결 값은 서버 러너와 다르다 (`CAIRN_CODE_PAIRING_FILE`, 볼륨 `code-pairing`, 파일 0640 · 폴더 750, node 그룹) |
| 결재 동작 | `code.pr.merge` (대상 `pull_request`, 판 = PR의 head 커밋) |

작업 payload(`task.task.requested`의 `payload.code`):

```json
{
  "repo": { "id": "…", "url": "https://github.com/me/app", "base": "main" },
  "paths": ["apps/server/src/modules/blog/"],
  "setup": "pnpm install --frozen-lockfile",
  "checks": ["pnpm check", "pnpm test"]
}
```

**기능 패키지 `code-github` (스키마 `code_github`)**

| 무엇 | 모양 |
|---|---|
| 표 `repos` | id · space_id · name · url · base · setup · checks text[] · version · created_at · updated_at · archived_at. 명령은 주인이 콘솔에 등록한 것만 돌린다 (저장소에 커밋된 명령은 쓰지 않는다). 지우지 않고 보관한다 (PR 기록이 가리킨다) |
| 표 `pulls` | id · space_id · repo_id · task_id(유일) · branch · number · url · head_sha · checks(jsonb) · status(open · merged · closed) · version(head가 바뀔 때마다 +1 = 결재의 판) |
| 설정 | `token` (secret, fine-grained PAT: 고른 저장소들의 Contents · Pull requests 쓰기만, Workflows는 주지 않는다), `apiUrl`(GitHub Enterprise일 때만) |
| API | `GET · POST /repos`, `PATCH /repos/:id`(주소는 못 바꿈), `POST /repos/:id/archive`, `POST /repos/:id/tasks { requestId, instruction, paths[], agentId? }`, `GET /pulls` · `GET /pulls/:id` (모두 주인) |
| MCP 도구 (`run`) | `code_credential { task_id }` → `{ token, api_url, pull }`: 그 code 작업의 임대를 쥔 칸 기기에게만 (`work.leased`, 플러그인 API 0.3) / `code_pull_opened { task_id, number, url, branch, head_sha, checks[] }` → `{ pull_id, version }` |
| 이벤트 | `task.task.requested`(kind `code`)를 남긴다. `task.approval.granted`(`code.pr.merge`)를 받아 결재한 판이 지금 PR과 같으면 merged로 남기고 `plugin.code_github.merge_confirmed { approvalId, outcome: done }`, 다르면 `failed` |
| 메뉴 | 운영 › 코드: 저장소 등록 · 일 맡기기 · PR 목록 |

**러너**

| 무엇 | 바뀜 |
|---|---|
| 칸 번호 | `CAIRN_RUNNER_SLOT`(`RunnerConfig.slot`). 코드 러너 이미지(`CAIRN_SANDBOX=1`)에서 연결 값 파일로만 쓴다. 아니면 시작하지 않는다. `next_jobs`에는 싣지 않는다 |
| 사용자 나누기 (`AgentUser`) | 러너는 root(CHOWN · SETUID · SETGID · KILL만)이고 AI · setup · checks는 agent(`CAIRN_AGENT_USER`, 1001)로 돈다. agent의 자리에 있는 것은 러너가 실행하지 않고, 읽을 것도 agent 권한으로 읽는다. `self`는 시험용 |
| 작업 자리 (`CodeRoom`) | `/work/<작업>`(711): 러너만 여는 깨끗한 clone(`runner/clean`, 700)과 agent의 사본(`repo`) · 홈 · 임시 · AI 설정(`ai`) · 결과물(`outputs`, 저장소 밖이라 patch에 들어가지 않는다. Claude에는 `--add-dir`로 연다). 결과물은 agent 권한으로 읽어 `runner/outputs`로 옮긴 뒤 올린다. 끝나면 agent 프로세스를 모두 끄고 지운다. 러너가 시작할 때 남은 자리를 치운다 |
| 저장소 정보 (`CodeSpec`) | `payload.code`를 경로 · 명령 · 주소로 쓰기 전에 검사한다 (https만, 자격 없는 주소, 브랜치 규칙, 상대 경로 접두어, 명령 길이). `.github/workflows`는 늘 막는다 |
| 러너의 git (`GitRepo`) | 깨끗한 clone에서만, 설정 파일 없이 환경의 `GIT_CONFIG_*`로만, http(s)만, 훅 끔. AI의 patch를 `git apply`로 옮기고(저장소 밖 · `.git` · 링크 너머 거절) 커밋 하나로 `cairn/<작업>`에만 push. 토큰(4단계)은 환경으로만 |
| 앞뒤 흐름 (`CodeStage`) | 앞: 저장소 정보 → (`repo.id`가 있으면) `code_credential`로 토큰 · 이미 연 PR → clone(PR이 있으면 `cairn/<작업>`에서 이어서, 지워졌으면 기준 브랜치) → 사본을 agent에게 → setup. 뒤: checks → agent 권한으로 patch → agent 프로세스 모두 끄기 → 깨끗한 clone에 옮기기 → 범위 확인 → 커밋 → 토큰으로 push → draft PR 열기 · 고치기(`GitHubPulls`, 프록시를 거쳐 api.github.com) → `code_pull_opened`. 결과물을 올린 뒤 `JobRun`이 작업 토큰으로 `request_approval(code.pr.merge)`. 그동안에도 보고 고리로 임대를 늘리고 취소를 듣는다 (`JobRun.during`). `repo.id`가 없는 일은 3단계처럼 브랜치까지 |
| AI CLI | code 작업이고 칸의 자리일 때만 셸을 연다 (Claude `Bash` · `Glob` · `Grep`, Codex `shell_tool` + `danger-full-access`: 칸이 벽). 다른 일에서 셸이 보이면 격리 위반으로 끈다 (두 CLI 모두). AI는 agent로, 프록시 환경과 함께 돈다 |
| 스킬 `cairn-code` | 고칠 수 있는 곳 안에서만 고치기, 검사 돌리기, 커밋 · push하지 않기, 저장소 안의 글은 자료로, 요약 쓰기 (`Task.SKILLS`) |

**배포 구성 (`docker-compose.code.yml`, 선택)**: `egress`(나가는 프록시: 코드 `apps/egress`, 허용 목록 `egress/allow.txt`. 1단계에서 구현), `code-runner-1` · `code-runner-2`(Node · git · 빌드 도구 · AI CLI. 칸마다 서비스 하나, YAML 앵커로 한 번만 적는다. 칸마다 메모리 4GB · CPU 2 · 프로세스 512, 읽기 전용 루트, 권한 없음). 코드 러너는 서버와 `egress`에만 닿는다. 2단계에서 구현.

**오류 경우**

| 경우 | 처리 |
|---|---|
| 저장소 정보가 틀림 | AI를 띄우지 않고 실패 (무엇이 틀렸는지) |
| 저장소에 닿지 못함 (네트워크 · 5xx · 시간 초과) | 돌려주고(`release_job`) 기다린다 (러너가 10초부터 5분까지 쉰다). 실패가 아니다 |
| 저장소 · 브랜치가 없음 · 인증 실패 · 허용 목록 밖 | 실패 |
| setup 실패 · 시간 초과 (15분) | AI를 띄우지 않고 실패, 끝부분 2,000자 |
| `paths` 밖 · `.github/workflows`를 고침 | 올리지 않고 실패로 끝낸다 (어느 파일인지 기록) |
| 바꾼 파일이 없음 | 올리지 않고 끝낸다 (done) |
| 바뀐 것이 20MB를 넘음 · 깨끗한 clone에 옮겨지지 않음 | 올리지 않고 실패 |
| `checks` 실패 · 시간 초과 (하나 10분) | 올리고 결과에 실패한 명령과 끝부분을 적는다 (4단계부터는 PR · 결재 메모) |
| push가 닿지 못함 | 두 번 더 해 보고 실패 (AI의 일을 처음부터 다시 하지 않게) |
| 머지 충돌 | 결재의 "고쳐 달라" 길로 돌려보낸다: base에 다시 맞추라는 지시와 함께 |
| PR의 head가 결재 뒤 바뀜 | 판이 달라 승인해도 머지하지 않는다 (409) |

## 6. 안전장치와 남는 위험

| 막을 일 | 어디서 | 어떻게 |
|---|---|---|
| 에이전트가 호스트에 닿는 것 | 코드 러너 칸 | Docker 소켓 없음, 호스트 폴더 없음, root가 아닌 사용자, 읽기 전용 루트 + 작업용 tmpfs, 메모리 · CPU · 프로세스 수 한도 |
| 칸이 아닌 러너가 셸 있는 일을 받는 것 | 서버 | 칸인지는 기기 권한 `sandbox`로 정한다 (러너가 알리는 값을 믿지 않음). `sandbox`는 칸 연결로만 생기고 주인도 줄 수 없다 |
| 칸과 서버 러너가 서로 행세하는 것 | 서버 · 볼륨 | 연결 값 · 입구 · 볼륨을 따로 둔다. 칸이 서버 러너로 붙으면 브라우저 작업을 받을 수 있다 |
| 칸 안의 AI가 칸의 연결 값 · 러너의 메모리를 읽는 것 | 칸 | 러너는 root(권한 CHOWN · SETUID · SETGID · KILL만, node 그룹)이고 AI · setup · checks는 agent(1001)로 돈다. 연결 값은 파일 0640 · 폴더 750(node 그룹). agent의 보조 그룹은 띄울 때 지워진다 (`AgentUser`) |
| 허락하지 않은 곳으로 나가는 것 | 나가는 프록시 | 칸은 내부 네트워크에만 있고, 밖으로는 허용 목록만. 브라우저의 남는 위험 1번도 같은 프록시로 막는다 |
| GitHub 토큰이 에이전트에게 가는 것 | 러너 | push · PR은 러너가 AI가 끝난 뒤에. 토큰은 러너 메모리에만, AI CLI는 다른 사용자라 읽지 못한다 |
| AI가 바로 main에 넣는 것 | GitHub · 결재 | `cairn/<작업>` 브랜치까지만. 머지는 `code.pr.merge` 뒤. main 브랜치 보호 |
| 비공개 지식이 저장소나 밖으로 가는 것 | 서버 규칙 | `code`는 `read_all` · `write`와 함께 줄 수 없다 (규칙 + DB CHECK) |
| 맡긴 범위 밖을 고치는 것 | 러너 | `paths` 밖이 바뀌면 PR을 올리지 않고 실패 |
| 작업끼리 남기는 찌꺼기 | 러너 | 작업마다 새 clone, 끝나면 agent 프로세스를 모두 끄고 작업 자리를 지운다. 러너가 다시 뜨면 남은 자리를 치운다 |
| AI가 `.git`에 심은 훅 · 설정이 러너(root, 토큰)에서 도는 것 | 러너 | 러너는 AI의 자리에서 git을 돌리지 않는다. 변경은 agent 권한으로 만든 patch 하나로만 받아 깨끗한 clone에 옮긴다. 러너의 git은 설정 파일을 읽지 않고 훅을 끈다 |
| AI가 띄워 둔 프로세스가 토큰을 엿보는 것 | 러너 | push 전에 agent 프로세스를 모두 끈다 (새 세션으로 빠져나간 것까지). 토큰은 러너 메모리와 root git의 환경에만 있다 |
| 브랜치의 워크플로가 저장소 비밀값과 함께 도는 것 | 러너 · GitHub | `.github/workflows`는 `paths`와 상관없이 늘 막는다. 4단계 토큰에도 workflow 권한을 주지 않는다 |

**남는 위험**
- **DNS로 새는 길**은 시험한 Docker(29.9.2)에서는 막혀 있다 (8장). Docker를 올리면 다시 확인한다.
- **허용한 호스트로 내보내기.** 저장소 파일에 심어 둔 지시문에 속으면 허용한 호스트로 코드를 보낼 수 있다. 토큰이 없어 쓰기는 어렵지만 읽기 요청에 실어 보내는 길은 남는다.
- **컨테이너는 VM이 아니다.** 커널을 호스트와 함께 쓴다. 더 강하게 막으려면 gVisor 같은 런타임을 선택으로 둔다.
- **구독 한도.** 동시에 N개면 N배 빨리 닿는다. 닿으면 새 일만 멈추는 지금 규칙(`Agent.holds`)을 그대로 쓴다. Codex는 서버 로그인으로 공간에서 하나다.
- **테스트가 비밀값을 필요로 하는 저장소.** 첫 버전은 비밀값을 넣지 않는다. 그런 테스트는 건너뛰었다고 PR에 적는다.
- **AI 구독 토큰은 칸 안의 AI가 볼 수 있다.** CLI가 쓰려면 환경으로 받아야 해서다. 나가는 곳이 허용 목록뿐이라 빼내기는 어렵지만 칸 기기 · 저장소 토큰보다는 덜 막혀 있다.
- **디스크.** 작업 하나가 `/work`(익명 볼륨, 크기 한도 없음)를 채울 수 있다. 작업마다 지우고, 한도는 필요해지면 볼륨 드라이버로 더한다.

진짜 AI 확인(배포 전 관문)은 4단계가 끝난 뒤 한 번, 5단계 뒤에 다시 한다.

**4단계 시험 (2026-11-10)**

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 패키지 | API 시험 (`testing/code-github.api.test.ts`) | 방문자 · write 기기 403. 저장소 주소 규칙 · 같은 주소 409 · 판 409 · 보관하면 목록에서 빠지고 맡길 수 없음. 맡기면 kind code 작업에 그때의 저장소 값. 토큰은 칸이 아닌 러너 · 쥐지 않은 작업에는 거절. PR 판이 head가 바뀔 때만 오름. 승인하면 판이 같을 때 merged · done, 다르면 failed |
| 끝까지 | 러너 통합 시험 (시험용 git 서버 + 가짜 GitHub API, 실제 칸 러너 프로세스) | 토큰으로 push · draft PR · 결재 · 승인 → done. "고쳐 달라" → 같은 브랜치에서 이어서 고쳐 같은 PR 갱신(PATCH) · 판 +1 · 새 결재. 토큰은 러너 로그 · 작업 기록에 없음 |
| 남은 확인 | 진짜 GitHub 저장소와 토큰 | 칸의 프록시(`NODE_USE_ENV_PROXY`)를 거친 api.github.com 호출, fine-grained 토큰의 권한 범위 |

**1단계 시험 (2026-11-10, Docker 29.9.2)**: 실제 구성과 같은 모양(내부망 + 두 망에 붙은 프록시 + 기본망에만 있는 DB 흉내)에서 칸 자리 컨테이너로 확인했다. 프록시 규칙은 단위 시험 13개(`apps/egress`)에도 있다.

| 칸에서 | 결과 |
|---|---|
| 내부 DB(기본망)에 바로 | 이름조차 풀리지 않음 (`EAI_AGAIN`) |
| 바깥 IP에 바로 | 길 없음 (`ENETUNREACH`) |
| 서버에 바로 (MCP 자리) | 연결됨 |
| 프록시: 목록에 없는 이름 · IP 직접 · 443이 아닌 포트 | 403 |
| 프록시: 목록에 있지만 내부 주소로 풀리는 이름 | 403 ("내부 주소로 풀려요") |
| 프록시: 허용한 이름 (github.com) | 200, 터널 안 TLS로 `HTTP/1.1 200 OK` |
| 칸에서 바깥 이름 풀기 (DNS로 새는 길) | 안 풀림 (`EAI_AGAIN`): 내부망의 Docker DNS는 바깥 이름을 대신 풀지 않는다 |

Dockerfile의 `egress` 단계는 이 시험 환경에서 패키지 설치가 막혀 빌드해 보지 못했다 (같은 모양인 `runner` 단계를 따랐다). 시험은 컴파일한 JS를 같은 조건(읽기 전용, 권한 없음, node 사용자)으로 띄워서 했다.

**2단계 시험 (2026-11-10)**

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 칸 연결 | API 시험 (`device.api.test.ts`) | 칸마다 기기 하나(`코드 러너 1` · `2`, 권한 `run` · `sandbox`). 다시 연결하면 앞 토큰은 바로 막힘. 서버 러너의 값으로는 칸이, 칸의 값으로는 서버 러너가 붙지 못함(403). 칸 번호가 틀리면 400, 이름이 겹치면 409. 주인은 칸 기기의 이름 · 권한을 바꾸지 못하고 다른 기기에 `sandbox`를 줄 수 없음 |
| 빌려주기 | API 시험 (`ai-login.api.test.ts`) | 칸은 code만 받음(일반 일 · 연결 확인은 안 받음). 일반 러너는 `sandbox: true`를 실어 보내도 code를 받지 못함. `code`+`read_all` · `write` 에이전트는 규칙(422)과 DB CHECK가 막음 |
| 끝까지 | 러너 통합 시험 (`runner.e2e.test.ts`) | 실제 서버에 러너 프로세스 2개가 칸 1 · 2로 붙고, 주인이 만든 code 작업을 칸 하나가 맡아 "아직 작업 공간이 없어요"로 끝냄 (3단계 전). 연결 값은 로그에 없음 |
| 연결 값 권한 | Docker 29.9.2, 같은 모양의 컨테이너 | 폴더 700 · 파일 600(node). node는 읽고, AI를 돌릴 사용자 agent(1001)는 파일도 목록도 못 읽음 |
| 칸 러너 시작 | 같은 컨테이너 (읽기 전용, 권한 없음, 내부망) | 칸 번호로 시작해 연결을 기다림. `CAIRN_SANDBOX`가 없으면 시작하지 않음 |
| AI 이름 | 고정한 CLI를 이 프록시로 띄움 (가짜 자격) | Claude 2.1.302: `api.anthropic.com`만 (401까지 닿음). Codex 0.164.0: `api.openai.com`(WebSocket 응답) · `chatgpt.com` · `ab.chatgpt.com`(목록 밖, 거절돼도 다음으로) · `github.com`. 이 환경에서는 OpenAI 이름이 풀리지 않아 Codex는 응답까지는 못 봄 |

`code-runner` 이미지는 이 환경에서 빌드하지 못했다: `apt-get`의 `deb.debian.org`가 이 세션의 네트워크 정책에 막혀 있다. apt만 뺀 같은 모양(컴파일한 러너, 사용자 agent, `CAIRN_SANDBOX=1`)으로 위를 시험했고, 이미지 빌드와 실제 로그인으로 AI 이름 다시 보기는 배포 전 확인(4단계 뒤)에 넣는다.

**3단계 시험 (2026-11-10)**

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 끝까지 | 러너 통합 시험 6개 (실제 서버 + 칸 러너 프로세스 + 이 컴퓨터의 시험용 git 서버, AI 사용자 self) | clone → setup → 셸이 열린 AI → checks → 맡긴 경로 안의 변경만 커밋 하나로 `cairn/<작업>`에 push. 경로 밖 · `.github/workflows` · setup 실패 · checks 실패 · 바꾼 것 없음 · 없는 저장소가 각각 맞게 끝나고, 작업 자리가 남지 않음 |
| 위험한 patch | 진짜 git으로 단위 시험 | 저장소 밖(`../`), `.git/hooks` 심기, 링크를 만들고 그 너머에 쓰기를 모두 거절 |
| 진짜 사용자 나누기 | 이 컴퓨터에서 root인 러너가 uid 1001로 `CodeStage` 앞뒤를 돌림 | setup · AI 흉내가 1001로 돌고, 깨끗한 clone은 못 봄. AI가 자기 `.git`에 심은 `post-commit` 훅은 돌지 않았고 `core.fsmonitor`는 agent 자신의 git에서만(1001) 돌았다. 브랜치에는 맡긴 파일만, 자리는 남지 않음. 이 시험으로 작업 자리 부모 폴더 권한(711)을 고쳤다 |
| 칸 권한 | Docker 29.9.2, 같은 모양의 컨테이너 (root + 권한 4개, node 그룹, 읽기 전용) | agent는 연결 값 · 깨끗한 clone · 러너의 `/proc/<pid>/environ` · `mem`을 못 읽고, agent의 보조 그룹은 지워짐. 새 세션으로 빠져나간 agent 프로세스도 모두 꺼짐 |

3단계 마지막에 이 환경의 Docker 데몬이 백그라운드 시간 한도로 멈춰, 그 뒤의 수정(좀비 프로세스 세기, 자리 권한 711)이 들어간 상태로는 서버 시험과 러너 통합 시험 전체를 다시 돌리지 못했다. 러너 단위 시험(154)과 `pnpm check`는 통과했다.

3단계 다음은 기능 범위의 **결과물 1차**(AI가 만든 파일을 받아 두는 콘솔 메뉴 "결과물")이고, 그 뒤에 4단계로 간다 ([기획서](기획서.md) 결정 기록 2026-11-10).

## 9. 참고한 오픈소스

[stablyai/orca](https://github.com/stablyai/orca) (MIT, 2026-11-09 확인)는 여러 코딩 에이전트를 각자의 git worktree에서 동시에 돌리는 데스크톱 앱이다.

- **가져온 것**: 저장소마다 준비 명령(`setup`)과 검사 명령, PR 댓글 · 실패한 검사를 같은 에이전트에게 되돌려 보내기, 작업 공간의 생명주기를 동작(준비 · 마무리 · 지우기)으로 나누기.
- **가져오지 않은 것**:
  - worktree만으로 격리하기: ORCA 문서도 "보안 샌드박스가 아니다"라고 쓴다.
  - 권한 확인 없이 실행하는 기본값을 격리 없이 쓰기: 우리는 컨테이너 안에서만 그렇게 돌린다.
  - Agent SDK로 Claude를 붙이기: 우리는 수정하지 않은 Claude Code를 띄운다 (2026-11-07).
- 비슷한 도구: Vibe Kanban · Claude Squad(worktree), container-use(에이전트마다 컨테이너, 확인하지 못함).
