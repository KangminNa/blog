# Cairn 객체 설계 규칙

> 서버(`apps/server`)의 모든 코드가 따른다.
> 새 기능은 이 문서의 객체 종류와 단계로 나누어 인터페이스를 먼저 제안하고, 승인받은 뒤 구현한다.

---

## 1. 네 계층

```
[진입]  Controller(REST) · Tool(MCP) · Guard · ErrorFilter
          │  Input.from(raw)                      ▲ View (엔티티.view() 또는 Query)
          ▼                                       │
[응용]  Service (쓰기: C·U·D)               Query (읽기: R → View)
          │  트랜잭션은 여기서만 연다               │  읽기 전용 SQL
          ▼                                       │
[도메인] Entity · Policy · Actor         │
          ▲  DB·Nest·시계를 모름                    │
[저장]  Repository · Gateway ─────────────────────┴──▶ Postgres · GitHub · SMTP · 파일
```

의존은 위에서 아래로만 흐른다. 도메인은 다른 계층을 모르고, 저장 계층이 도메인 객체를 만들어 올려 준다.

---

## 2. 객체 종류

아래 종류 말고는 만들지 않는다. 파일 이름의 끝이 곧 종류다.

| 계층 | 종류 | 파일 | 맡는 것 | 하지 않는 것 |
|---|---|---|---|---|
| 진입 | **Controller / Tool** | `*.api.ts`(MCP·SSE 입구 포함) / `*.tool.ts` | 채널(REST·MCP)에서 요청 하나를 받아 Service나 Query 메서드 **딱 하나**를 부른다 | 분기, 판단, DB |
| 진입 | **View** | `*.view.ts` | 표의 칸 중 무엇을 내보내는지 적는 **유일한 곳**. Query와 엔티티가 같은 View를 쓴다. 보는 사람(방문자·주인·AI)마다 다르면 View를 나눈다 | 데이터 조회 |
| 진입 | **Guard** | `*.guard.ts` | 토큰·쿠키를 확인해 Actor를 만든다. 로그인 쿠키로 오는 쓰기 요청은 출처(`Sec-Fetch-Site`·`Origin`)가 이 사이트일 때만 받는다 | 권한 판단 |
| 진입 | **Handler** | `*.handler.ts` | 일꾼이 넘긴 이벤트 하나를 받아 Service를 부른다. 같은 이벤트가 두 번 와도 결과가 같게 | 판단, 트랜잭션 |
| 진입 | **Job · Action** | `*.job.ts` · `*.action.ts` | 간격마다 도는 일 / 주인이 누르는 동작. Service·Query·Gateway를 부른다 | 판단 |
| 진입 | **일꾼** | `platform/worker/outbox-worker.ts` | 저장 신호(`cairn_outbox`)로 깨어나고 30초마다 한 번 더 확인한다. outbox 이벤트를 빌려 Handler에 넘기고, 실패는 늦춰서 다시, 반복 작업을 돌린다 (`main.worker.ts`) | 비즈니스 |
| 응용 | **Input** | `*.input.ts` | 유스케이스 입력. `static from(raw)`로 **모양**(필드 유무, 자료형)을 검사한다. 표의 칸은 낱개가 아니라 `changes` 묶음으로 넘긴다 | 의미 검사 |
| 응용 | **Service** | `*.service.ts` | 데이터 묶음 하나의 **쓰기(C·U·D) 전부**. 트랜잭션을 열고 불러오기 → 엔티티에 시키기 → 저장 순서를 정한다 | 비즈니스 판단, 다른 Service 호출 |
| 응용 | **Query** | `*.query.ts` | 같은 데이터의 **읽기(R) 전부**. 화면·AI가 함께 보는 묶음(View)을 SQL로 바로 만든다. Actor를 반드시 받아 공개 범위를 거른다 | 쓰기, 엔티티 반환 |
| 도메인 | **Entity** | `<이름>.ts` | 표 한 줄과 그 규칙. 행은 안에 숨기고 동작과 `view()`만 내놓는다. 묶음 안에 딸린 데이터(예: 세션의 판)도 함께 다룬다 | DB, Nest, 외부 호출 |
| 도메인 | **Policy** | `*.policy.ts` | 엔티티 하나에 담을 수 없는 판단 (민감정보 제거, 공개 기본값 등) | 상태 보관 |
| 도메인 | **Actor** | `platform/base/actor.ts` | 요청한 주체와 그가 할 수 있는 일. `OwnerActor` · `DeviceActor` · `AgentActor`(작업 토큰) · `ApprovedActor`(결재 뒤 일꾼의 실행) · `SystemActor` · `VisitorActor`. 만드는 건 account 모듈의 Guard | — |
| 저장 | **Repository** | `*.repository.ts` | 데이터 묶음 하나를 불러오고·잠그고·저장한다 | 판단, View 만들기 |
| 저장 | **Gateway** | `*.gateway.ts` | DB 밖의 외부 세계 (GitHub, SMTP, 파일 저장소) | 판단 |
| 공통 | **Error** | `platform/base/errors.ts` | 처리 단계별 실패 (3장) | — |
| 공통 | **Event** | `platform/base/event.ts` | 모듈 사이에 "무슨 일이 있었다"를 알리는 메시지 (9장) | — |

## 3. 요청 처리 단계

### 쓰기

| 단계 | 담당 | 실패 | REST | MCP (AI에게) |
|---|---|---|---|---|
| ① 인증 | Guard → Actor | `Unauthenticated` | 401 | 다시 연결하라고 안내 |
| ② 요청 해석 | `XxxInput.from(raw)` | `InvalidRequest` (모양) / `TooLarge`(본문 한도) / `UnsupportedType`(파일 형식) | 400 / 413 / 415 | 고칠 필드 목록 |
| ③ 권한 | `actor.assertCan(...)` (Service 첫 줄) | `Forbidden` / `TooManyRequests`(설치 코드처럼 마구 찔러보기) | 403 / 429 | 필요한 권한 |
| ④ 불러오기 | Repository `lock`·`load` (트랜잭션 시작) | `NotFound` | 404 | |
| ⑤ 규칙 | Entity 메서드, Policy | `RuleViolation` / `Conflict`(version) | 422 / 409 | 무엇이 어긋났는지 |
| ⑥ 저장 | Repository `save` + outbox | `Busy`(DB 시간 제한: 잠금 5초 · 쿼리 30초) / 그 밖의 DB 오류 | 503 / 500 | busy면 잠시 뒤 다시 |
| ⑦ 응답 | `entity.view()` | — | 200 | |

### 읽기

① 인증 → ② 요청 해석 → `Query(actor, ...)` → View → ⑦ 응답

Error 종류는 단계마다 진입 계층의 처리가 다르기 때문에 나눈다. ErrorFilter 하나가 위 표대로 REST 상태 코드와 MCP 응답으로 바꾼다.
DB 시간 제한 오류는 트랜잭션 밖 읽기에서도 나므로 입구(REST 필터 · MCP 입구)에서 `Database.busy`로 `Busy`가 된다.

## 4. 호출 규칙

| 규칙 | 막는 문제 |
|---|---|
| Controller·Tool은 Service나 Query 메서드를 하나만 부른다 | 진입 계층에 비즈니스가 새고, REST와 MCP의 동작이 달라짐 |
| 쓰기는 반드시 엔티티를 거친다 (불러오기 → 메서드 → 저장) | SQL 한 줄로 규칙을 우회함 (예: 사람이 고친 칸을 AI가 덮어씀) |
| 읽기는 엔티티를 거치지 않는다 (Query가 View를 바로 만든다) | 목록·그래프에서 엔티티 수천 개를 만들었다 버림 |
| Query는 Actor 없이 호출할 수 없다 | 공개 여부를 거르는 걸 깜빡해 비공개 세션 노출 |
| 트랜잭션은 Service만 연다. 커맨드 하나 = 트랜잭션 하나. 트랜잭션 안에서 외부 호출·AI 대기 금지 | 잠금이 오래 잡힘, 트랜잭션 경계가 흩어짐 |
| Service는 다른 Service를 부르지 않는다. 판단 재료가 필요하면 같은 모듈의 Query로 읽는다 (예: 로그인할 때 설치 상태) | 트랜잭션 중첩, 순환 의존 |
| Service는 데이터 묶음 하나의 Repository만 쓴다. **예외는 vault의 `ChangeService` 하나**: 변경 묶음(git의 커밋)을 적용하려면 세션·wiki·카테고리·선을 한 트랜잭션에서 바꿔야 한다. 판단은 엔티티와 `ReviewPolicy`가 하고, `ChangeService`는 순서만 정한다 | 한 변경이 여러 묶음에 걸칠 때 트랜잭션이 쪼개지거나 Service끼리 부르게 됨 |
| 다른 모듈은 그 모듈의 `index.ts`가 내보낸 것만 쓴다. Entity·Repository는 모듈 안에만 | 모듈이 깊이 얽혀 나눌 수 없게 됨 (9장) |
| View는 받은 행으로만 만든다 | 응답을 만들다 DB를 또 조회함 |

## 5. Input은 응용, View는 진입

- **입력은 채널이 달라도 같다.** 세션 저장은 MCP로 오든 REST로 오든 같은 `SaveSessionInput`이다 (`session.input.ts`). 그래서 유스케이스(응용) 소유다.
- **출력은 보는 사람마다 다르다.** 같은 세션도 방문자는 공개 칸만, 주인은 기기·판 기록까지, AI는 경고·알림까지 본다. 그래서 View를 사람마다 나눈다.

## 6. 폴더와 표

데이터 묶음 단위로 폴더를 만든다. **데이터 묶음**은 항상 같이 바뀌어야 하는 데이터다. 세션과 그 판들은 판 번호·현재 판·버전이 함께 맞아야 하므로 한 묶음이다.

```
apps/server/src/modules/<모듈>/
  <모듈>.tables.ts           표 인터페이스. 자동 생성 (pnpm db:rows)
  <모듈>.schema.ts           조건 규칙이 쓰는 표의 이름 · 칸 · 행 타입 (Drizzle 표). 자동 생성 (pnpm db:rows)
  <묶음>/
    <이름>.ts                Entity
    <이름>.view.ts           내보내는 칸
    <이름>.input.ts          입력 검사
    <이름>.service.ts        쓰기와 트랜잭션
    <이름>.query.ts          읽기
    <이름>.api.ts            REST 진입
    <이름>.api.test.ts       보는 사람별 결과 (방문자 · write 기기 · 주인)
    <이름>.tool.ts           MCP 진입 (있을 때만)
    <이름>.repository.ts     저장
```

한 데이터의 C·R·U·D는 한 폴더, 한 Service, 한 Query에 모인다. 새 묶음은 `pnpm new:bundle`로 만든다 (아래 "콘솔 메뉴 하나의 구조").

파일 이름은 위의 것만 쓴다 (`pnpm check`의 구조 검사, 아래). View는 Query 파일 안이 아니라 `.view.ts`에 둔다. 도구가 여럿이면 `<이름>.tool.ts` 한 파일에 함께 둔다 (`task/task/task.tool.ts`, `vault/session/session.tool.ts`).

### 콘솔 메뉴 하나의 구조

```
apps/server/src/modules/<모듈>/<묶음>/   위의 파일들
apps/web/app/admin/<주소>/
  page.tsx                   틀 (제목. 서버에서 첫 데이터를 읽을 때만 serverGet)
  <이름>Panel.tsx            'use client'. client-api로 서버 API를 부르고 useNotify로 알린다
apps/web/app/_<모듈>/types.ts   여러 메뉴가 함께 쓰는 응답 타입 (view에서 ReturnType으로)
apps/web/app/admin/menu.tsx     메뉴 한 줄 (그룹 · 주소 · 이름 · 아이콘)
```

- 응답 모양의 원본은 서버 `<이름>.view.ts`의 `toJSON()`이다. 웹은 `import type`으로 가져와 `ReturnType<XxxView['toJSON']>`로 쓰고 손으로 다시 적지 않는다. 서버 응답이 바뀌면 웹 타입 검사가 깨져 알려 준다. 한 메뉴만 쓰면 패널 파일 안에, 여럿이 쓰면 `_<모듈>/types.ts`에 둔다.
- 관리 일의 권한은 Service·Query 첫 줄에서 `assertOwner()`로 묻는다(명령줄도 부르면 `assertOwnerOrSystem()`). `assertCan(WRITE)`는 write 기기도 통과한다. AI 토큰(기기·작업)은 `/mcp`에서만 요청자가 되어 REST에서는 방문자와 같지만(`ActorGuard`), 관리 일은 Service에서도 막는다 (두 겹).
- 생성기: `pnpm new:bundle <모듈>/<묶음> [--menu <그룹>/<이름>] [--tool] [--plural <복수형>]`. 위 파일들을 만들고, `<모듈>.tables.ts` · `<모듈>.schema.ts` 끝에 새 표의 인터페이스와 Drizzle 표(출력한 마이그레이션과 같은 모양)를 붙인다. 모듈 등록·도구 목록·메뉴 한 줄과 마이그레이션 SQL은 출력만 한다. 만든 직후 `pnpm check`는 메뉴 한 줄(`--menu`일 때)만 알려 주고, 생성된 API 테스트는 등록·마이그레이션 전까지 실패한다. 마이그레이션 뒤 `pnpm db:rows`가 붙여 둔 것을 DB에서 다시 만든다 (그 전에는 `pnpm db:check`가 알려 준다). 템플릿은 `scripts/templates/bundle/`이고 `TableEntity` · `TableRepository` · `EntityService` 방식이다.
- 구조 검사 (`pnpm check` → `scripts/check-structure.mjs`): ① 파일 이름 (`.controller` · `.request` · `.response` 금지) ② REST 진입 옆에 `.api.test.ts`(다른 파일에서 시험하면 `TESTED_ELSEWHERE`에 그 파일) ③ 메뉴와 `app/admin/<주소>/page.tsx`가 짝 ④ `app/_lib/types.ts`에 손으로 적는 타입은 오류 모양(`ApiError`)뿐이다.

### 칼럼 하나는 기능 하나가 아니다

표 하나는 인터페이스 하나다. 계층마다 칼럼을 낱개로 들고 다니지 않고, 칼럼을 아는 곳을 세 곳으로 제한한다.

| 곳 | 하는 일 | 칼럼을 더하면 |
|---|---|---|
| `<모듈>.tables.ts` · `<모듈>.schema.ts` | 표의 모양(행 타입, 조건 규칙이 쓰는 Drizzle 표). 마이그레이션에서 생성하고 `pnpm db:check`가 어긋남을 잡는다 | `pnpm db:rows` |
| Entity의 `RULES`와 Input의 `COLUMNS` | 밖에서 바꿀 수 있는 칸과 그 규칙, 입력 모양 | 사람이 바꾸는 칸이면 각 한 줄 |
| View의 `toJSON` | 밖으로 내보내는 칸 | 내보낼 칸이면 한 줄 |

Repository, Service, 생성자, `open`, `restore`, Query는 칼럼을 모른다. 칼럼 이름을 고치거나 지우면 쓰는 곳에서 컴파일 오류가 난다.
칸을 다른 형식으로 옮기는 곳은 따로 안다: AI 변경(`ChangeOp`), 보관 파일, 복원. 예를 들어 `Category.color`는 생성된 표 말고도 7개 파일에 있다.

```ts
// Entity: 행은 안에 있고, 바꾸는 길은 규칙과 동사뿐이다
export class Agent extends TableEntity<AgentRow, AgentNew> {
  private static readonly RULES: ColumnRules<AgentRow> = {
    five_hour_limit: (value) => { /* 검사 */ return value; },
  };
  static restore(row: AgentRow): Agent { return new Agent(row); }
  edit(changes: Partial<AgentRow>): void { this.accept(changes, Agent.RULES); }
  pause(): void { this.moveTo(Agent.PAUSED); }
  view(): AgentSavedView { return new AgentSavedView(this.row); }
}

// Repository: 표(생성된 <모듈>.schema.ts의 Drizzle 표)와 그 표만의 SQL
export class AgentRepository extends TableRepository<AgentRow, Agent> {
  protected readonly table = agents;
  protected readonly noun = '에이전트';
  protected toEntity(row: AgentRow): Agent { return Agent.restore(row); }
}

// Service: 순서는 기반이 하고 엔티티에게 시킬 일만 적는다
update(actor: Actor, req: UpdateAgentInput): Promise<Agent> {
  return this.changeAsOwner(actor, req, (agent) => agent.edit(req.changes));
}
```

- **Entity**: `TableEntity<Row, New>`를 상속한다. 표 한 줄을 `row`로 읽고(읽기 전용), `put`이나 `accept`로만 적는다. `get`은 다른 객체가 판단에 쓰는 값만 둔다. Repository나 응답을 위한 `get`은 두지 않는다. `status`처럼 규칙이 있는 칸은 `RULES`에 넣지 않고 동사 메서드로만 바꾼다.
  열쇠가 `id`가 아니거나 `version` 칸이 없는 표(`OAuthClient` · `AuthorizationCode` · `Asset` · `PluginState` · `PlanUsage`)는 `BaseEntity`를 상속해 행을 들고, 저장할 행을 `unsaved`로 내놓는다.
  딸린 표만 바뀌어도 저장하면 `version`을 올려야 하면(화면이 든 것이 옛것이 되게) `unsaved`를 덮어써 칸 하나를 돌려준다 (`Space` · `Device`).
- **Repository**: `load` · `lock` · `save`는 기반이 한다. 다른 표를 함께 읽으면 `select`를, 딸린 표를 저장하면 `saveParts`를 덮어쓴다. 없을 수도 있는 대상은 `lockOrNull`. 한 줄이 엔티티 하나가 아닌 표는 `BaseRepository`를 그대로 쓴다.
- **Input**: 사람이 바꾸는 칸은 `COLUMNS`에 한 줄씩 적고 `f.columns(COLUMNS)`로 읽어 `changes`로 넘긴다. API 이름은 칸 이름의 camelCase다. 버전은 `f.version()`, id와 버전뿐이면 `VersionInput`.
- **Service**: 엔티티 하나를 고치면 `EntityService`의 `change` · `changeAsOwner`를 쓴다. 공간은 `actor.requireSpace()`.
- **View**: `.view.ts`는 표 인터페이스의 타입만 가져오고(`import type`) 그 밖에는 아무것도 가져오지 않는다. 웹이 `ReturnType<XView['toJSON']>`로 가져온다. 행을 펼쳐(`...row`) 내보내지 않는다: 새 칼럼이 저절로 나가면 안 된다 (원칙 5). 보는 사람마다 내보낼 칸이 다르면 View를 나누고(방문자용은 `Public…`) Query가 고른다 (`PostView` · `PublicPostView`, `PluginListView` · `PluginSummaryListView`). 쓰기 결과처럼 Query를 거치지 않으면 엔티티의 `view(actor)`가 고른다.
- **Query · Repository의 쿼리**: 행을 View(엔티티)에 그대로 넘긴다. `String(row.x)` 같은 손 변환은 없다. 쿼리는 누가 맡는지로 나눈다.
  - **코어의 조건 규칙** (`platform/base`의 `TableQuery`): 표 하나의 읽기와 쓰기. 기능 코드는 조건만 적는다: `this.rows(tasks, { space_id: s, status: ['queued', 'running'] }, { order: ['id desc'], limit: 20 })`.
    값 `=`, 목록 `= ANY`, `null`은 `IS NULL`, `Rule.set`은 `IS NOT NULL`, `Rule.before` · `atMost` · `after` · `atLeast` · `not` · `like`는 비교, `Rule.maybe(값)`은 값이 없으면 조건을 뺀다. 빠진 값(`undefined`)은 오류다 (공간 조건이 실수로 빠지지 않게).
    방법은 `{ columns, order, limit, lock: true | 'skip' }`. 칸 이름은 생성된 표에서 타입을 받아 틀리면 컴파일 오류이고, 표에 없는 칸은 실행 전에 막는다.
    같은 모양(표 · 조건의 종류 · 방법)은 처음 한 번만 SQL 글자로 만들어 기억하고 다시 쓴다. 실행은 부를 때의 `postgres` 연결(트랜잭션이든 아니든)로 해서 행 모양(Date · bigint · jsonb)이 직접 쓴 SQL과 같다.
    읽기는 `rows` · `row` · `exists`(Query · Repository), 엔티티로는 `find` · `findOne`(TableRepository의 표), 쓰기는 `insertRows` · `updateRows`(`Rule.now`는 DB 시각) · `deleteRows`(Repository), 목록 한 쪽은 `pageOf`.
  - **패키지(모듈)의 쿼리** (`this.sql<XRow[]>`): 그 기능에만 있는 쿼리. 표를 잇거나(JOIN · LATERAL) 모으거나(count · array_agg) 재귀 · 검색(pg_bigm) · JSON 경로를 쓰는 읽기, ON CONFLICT · RETURNING · 식이 있는 쓰기. 그 모듈의 Repository · Query가 가진다.
  - 표 하나를 id로 읽고 잠그는 것(`load` · `lock` · `lockOrNull`)은 `TableRepository`가 조건 규칙으로 한다.
- `.api.ts`나 `.input.ts`는 웹에서 가져올 수 없다. 데코레이터가 딸려 와 웹 타입 검사가 실패한다 (2026-11-01 시험: 오류 34개, `.view.ts`만 가져오면 0개).

## 8. 객체 안쪽의 규칙

- 데이터만 들고 다니는 클래스를 만들지 않는다. 데이터는 그것을 쓰는 객체의 필드다. 예외는 Input · View · Event뿐이다.
- 추상 클래스는 구현이 **지금** 둘 이상일 때만 만든다. "나중에 필요할 것 같아서" 미리 추상화하지 않는다. 예외는 10장의 기반 클래스다.
- 판단이 없는 열거값은 주인 클래스의 상수로 둔다 (예: `Session.ORIGIN`).
- 엔티티는 생성 메서드(`static open`, `static restore`)로만 만든다. `restore`는 행을 그대로 받는다.
- 같은 행위가 둘 이상이면 기반 클래스로 올린다. 모듈 안에서만 같으면 그 모듈의 추상 클래스로 둔다.
- `type`·`interface`는 표 인터페이스, 기반 클래스끼리의 약속, 표 행에 함께 읽는 칸을 더한 모양, 외부 라이브러리 타입에만 쓴다.

## 9. 모듈

서버는 지금 하나로 배포한다(모듈러 모놀리스). 다만 아래 다섯 가지를 지켜, 나중에 모듈을 별도 서버로 떼어낼 때 고칠 곳이 경계에만 있게 한다.

1. **테이블은 주인이 하나.** 모듈 = 스키마. 자기 스키마만 SQL로 읽고 쓴다. 모듈 사이에는 외래키를 두지 않는다.
2. **다른 모듈은 `index.ts`로만.** 모듈마다 `index.ts`에 밖에서 써도 되는 것(Service · Query · Input · View)만 내놓는다. Entity, Repository, 트랜잭션은 경계를 넘지 않는다. 떼어낼 때는 이 입구가 HTTP 호출로 바뀐다.
3. **다른 모듈에 생길 후속 일은 이벤트로.** 직접 부르지 않고, Entity가 `DomainEvent`를 기록하면 Repository가 저장할 때 같은 트랜잭션으로 `platform.outbox`에 남긴다. 이름은 `<모듈>.<데이터>.<과거형>`(예: `vault.session.saved`), 내용을 바꾸면 version을 올린다.
4. **요청자 정보는 값으로.** Actor는 종류·id·공간·권한만 가진다. 떼어내면 그대로 토큰 내용이 된다.
5. **platform은 공통 기반만.** 비즈니스 규칙을 두지 않는다. outbox처럼 같은 트랜잭션에 들어가야 하는 것은 호출한 쪽의 트랜잭션을 받는 클래스로 제공한다.

### 모듈 지도

지도의 원본은 `apps/server/modules.json`이다. `pnpm check`(코드)와 `pnpm db:check`(DB)가 이 파일로 검사한다.

| 모듈 | 하는 일 | 소유 스키마 | 데이터 묶음 | 써도 되는 모듈 |
|---|---|---|---|---|
| **platform** | 공통 기반: DB, 기반 클래스, 오류, outbox, 실시간 스트림, 파일, 알림, 임베딩 모델 | `platform` | 플러그인 (알림은 표만 있다) | 없음 |
| **account** | 블로그 공간·설정, 주인, 기기, 로그인 | `account` | 공간(설정 포함), 기기(토큰 포함) | platform |
| **vault** | 세션과 그래프, 제안, 변경 기록 | `vault` | 세션(판·첨부·편집 임대), wiki(판), 카테고리, 연결선, 변경 묶음(제안), 정리 설정, 글 자리 사본, 그래프 배치 | platform |
| **blog** | 글, 카테고리, 사진, 소재 | `blog`, `work` | 글(판·참고 기록·편집 임대), 카테고리, 사진, 소재 | platform, vault(읽기만) |
| **task** | 에이전트, 작업, 결재, 목표, 하트비트, 러너, AI 로그인 (스케줄은 7단계) | `task` | 에이전트, 목표, 하트비트, 작업(실행 기록), 결재, 구독 사용률, AI 로그인, 러너 | platform |
| **mcp** | AI 도구가 들어오는 입구. 도구 등록, 읽기 기록 | `mcp` | 없음 | platform, account, vault, blog, task |

- vault는 blog를 모른다. blog는 재료를 가져올 때만 vault의 Query를 쓴다.
- task는 blog·vault를 모른다. 결재가 끝나면 이벤트로 알린다 (13장).
- MCP 도구(`*.tool.ts`)는 각 모듈에 있다. 모듈마다 `<모듈>-tools.ts` 목록 하나에 도구를 더하고, mcp 모듈은 모듈별 목록을 모아서 연다.
- 이벤트 받기와 반복 작업은 모듈의 `onModuleInit`에서 `CoreWorkers`에 등록한다 (`on`, `every`). 꼭 받아야 하는 주제는 `expect`로 적으면, 받는 쪽이 없을 때 일꾼이 시작하지 않는다.
- 한 번의 쓰기가 같은 모듈의 여러 데이터 묶음을 바꿔야 하면(예: wiki 합치기), Service가 같은 모듈의 Repository 여러 개를 한 트랜잭션에서 쓸 수 있다. 바꾸는 건 모두 Entity 메서드로 하고, 잠금은 id 순서로 잡는다. 다른 모듈과는 한 트랜잭션에 묶지 않는다.

### 모듈 규칙 문서

모듈 폴더마다 `CLAUDE.md`를 같은 틀로 둔다: 하는 일 · 소유 데이터 · 데이터 묶음 · 공개 API(`index.ts`) · 내보내는 이벤트 · 받는 이벤트 · 써도 되는 모듈 · 지켜야 할 것 · 하지 말 것. 모듈의 동작을 바꾸면 그 모듈의 `CLAUDE.md`도 함께 고친다.

## 10. 기반 클래스와 외부 라이브러리

외부 라이브러리는 모듈 코드에서 바로 쓰지 않는다. `platform/base`의 기반 클래스가 라이브러리를 감싸고, 모듈의 객체는 그 기반 클래스를 상속한다. 라이브러리를 바꾸거나 더할 때는 기반 클래스만 고치고, 모듈은 필요한 부분만 하위 클래스에서 덮어쓴다.

| 기반 클래스 | 파일 | 공통으로 해 주는 것 |
|---|---|---|
| `Database` | `database.ts` | DB 연결, 트랜잭션. `postgres` 라이브러리를 가져오는 유일한 곳. 연결마다 시간 제한(`LIMITS`), 걸린 오류를 `Busy`로(`busy`), 시간 제한 없는 `unlimitedTransaction`은 복원 두 곳만 (platform/CLAUDE.md "DB 연결") |
| `BaseService` · `EntityService` | `base-service.ts` | 트랜잭션 열기. 잠그기 → 버전 확인 → 시키기 → 저장 (`change`, `changeAsOwner`) |
| `BaseQuery` | `base-query.ts` | 읽기 연결, 공개 범위 조건(`visibleTo(actor)`) |
| `TableQuery` · `Rule` · `TableReader` | `table-query.ts` | 코어의 쿼리 도구: 조건 규칙으로 표 하나를 읽고 쓴다(6장). 같은 모양은 한 번만 SQL로 만들고 기억한다. 표 이름 · 칸은 생성된 `<모듈>.schema.ts`에서 받고 SQL은 직접 만든다: Drizzle의 쿼리 빌더는 jsonb 값을 미리 바꿔 우리 연결에서 두 번 인코딩되고(2026-11-08 시험), Drizzle 클라이언트는 우리 연결의 날짜 읽기를 바꾼다. `drizzle-orm`을 가져오는 곳은 여기와 생성된 표뿐이다 |
| `BaseRepository` · `TableRepository` | `base-repository.ts` · `table-repository.ts` | 없으면 `NotFound`, 버전이 어긋나면 `Conflict`, 이벤트를 outbox에 남기기. 표 하나의 `load` · `lock` · `save` |
| `BaseEntity` · `TableEntity` | `base-entity.ts` · `table-entity.ts` | id(UUIDv7), 버전, 이벤트 기록. 행 숨기기, 바뀐 칸 기억, 규칙 통과 (`accept`) |
| `BaseRequest` · `RequestFields` · `VersionInput` | `base-request.ts` | 필드와 표의 칸 읽기(`columns`), 틀린 필드를 모아 `InvalidRequest` |
| `BaseGateway` | `base-gateway.ts` | 외부 호출의 시간 제한·재시도, 실패하면 `ExternalFailure` |
| `BaseTool` | `base-tool.ts` | MCP 도구의 이름·설명·권한·입력 모양(JSON Schema)·처리 약속. 권한이 없는 기기에게는 목록에도 안 보인다. 처리(`handle`)는 사이트 주소도 받는다 (응답의 관리 화면 링크용, MCP 입구가 넘김) |
| `Idempotency` | `idempotency.ts` | 같은 `request_id`는 한 번만 반영 (`platform.idempotency`). Outbox처럼 호출한 쪽의 트랜잭션 안에서 자리를 잡고(`previous`) 결과를 남긴다(`remember`). 같은 요청이 동시에 오면 뒤의 요청은 앞의 결과를 받는다 |
| `McpEndpoint` | `mcp-endpoint.ts` | MCP 입구(Streamable HTTP, 상태 없음). MCP SDK를 가져오는 유일한 파일. 도구 오류는 `DomainError.toJSON()`으로 AI에게 |
| `SecretBox` | `secret-box.ts` | 비밀값 암호화, 서버 키에서 값 만들기(`derive`), URL·쿠키에 싣는 짧은 값 싸기(`pack`·`unpack`: 용도와 만료 시각까지 암호문 안에. 용도는 필수이고 다른 용도로는 풀리지 않는다. 승인 요청, 설치 통행증, 로그인 확인값, 작업 토큰) |
| `AttemptLimiter` | `attempt-limiter.ts` | 짧은 시간에 너무 많이 시도하면 `TooManyRequests`. 모든 시도(`hit`) 또는 틀린 시도만(`check`·`fail`). IP로 셀 때는 `place(ip)`로 한 곳을 묶는다 (IPv6는 /64) |
| `PasswordHasher` | `password-hasher.ts` | 비밀번호를 되돌릴 수 없는 값으로 (Node 내장 scrypt). 저장값에 강도를 적어 두고 약하면 다시 저장 |
| `ZipFile` | `zip-file.ts` | zip 만들기 (Node 내장 zlib, 라이브러리 없음). 파일마다 deflate, 이름은 UTF-8, 시각은 고정. 앱에 올릴 스킬 묶음, 보관 형식 내보내기(zip) |
| `BlobStore` | `blob-store.ts` | 내용 주소 파일 저장소. 파일은 볼륨에 sha256 이름으로, 정보는 `platform.blobs`에 둔다. 트랜잭션 밖에서 부른다. 누구에게 보여 줄지는 파일을 가리키는 모듈이 정한다 |
| `SecretRotation` | `secret-rotation.ts` | 서버 키 교체. 비밀값을 가진 모듈이 다시 잠그는 방법을 `onModuleInit`에서 등록한다 (`pnpm secret:rotate`) |
| `SensitivePolicy` | `sensitive-policy.ts` | AI가 보낸 글의 비밀값을 판이 되기 전에 `[지움: 종류]`로 바꾼다 (`Redaction`). 모양만 보고 어느 칸을 지울지는 모듈이 정한다 |
| `Actor` | `actor.ts` | 요청자와 권한 |

일꾼 쪽 기반은 `platform/worker`에 있다: `CoreWorkers`(코어의 이벤트 받기·반복 작업 등록), `OutboxWorker`(코어와 플러그인에 전달).

- 기반 클래스는 얇게 둔다. 모든 하위 클래스가 똑같이 하는 일만 넣고, 한 모듈에만 필요한 건 그 하위 클래스에 둔다.
- Controller와 Policy에는 기반 클래스를 두지 않는다. 공통으로 할 일이 생기면 그때 만든다.
- 외부 라이브러리는 `platform/base` 안에서만 가져온다. 예외는 프레임워크(`@nestjs/*`)와 Node 내장 모듈(`node:*`)이다. `pnpm check`가 검사한다.

### 새 라이브러리가 필요해지면

넣기 전에 아래 순서로 근거를 보이고 승인받는다.

1. **겪은 문제**: 지금 구조로 무엇이 안 되는가. 실제로 생긴 일로 설명한다.
2. **들어갈 자리**: 어느 기반 클래스 아래에 들어가는가. 새 기반 클래스가 필요하면 왜 필요한가.
3. **비용**: 직접 만들 때와 비교한 코드 양, 딸려 오는 패키지 수.
4. **고치는 범위**: 모듈 코드를 고쳐야 하는가. 원칙은 "기반 클래스만 바뀐다".
5. **빼는 방법**: 나중에 빼거나 바꾸려면 무엇을 고치면 되는가.

예: ORM이 필요해지면 `Database`에 ORM 인스턴스를 더하고 `BaseRepository`에서 `this.orm`으로 쓸 수 있게 한다. 같은 연결을 쓰므로 기존 저장소는 그대로 두고, 필요한 저장소만 옮긴다.

---

## 11. 새 기능을 만들 때

1. 어느 모듈, 어느 데이터 묶음의 **쓰기**인가 **읽기**인가를 정한다.
2. 쓰기면 Input · Service 메서드 · Entity 메서드 · View를, 읽기면 Input · Query 메서드 · View를 정한다.
3. 3장의 단계별로 무엇이 실패할 수 있는지, 다른 모듈에 알려야 할 이벤트가 있는지 적는다.
4. 이 묶음을 인터페이스로 제안하고 승인받는다.

## 12. 플러그인

코어가 몰라도 되는 기능은 플러그인으로 만든다. 플러그인은 `plugins/<이름>/` 폴더 하나이고, 목록 파일(`cairn-plugin.json`)에 적은 확장 지점만 쓸 수 있다. 규칙과 형식은 `plugins/CLAUDE.md`.

**호스트 (platform/plugin)**

| 객체 | 맡는 것 |
|---|---|
| `PluginManifest` · `PluginSettingSpec` | 목록 파일을 읽고 검사한다 (이름, 버전, 지원 API 범위, 설정 칸, 웹 화면 자리, 서버 파일, `uses`). 들어 있는 플러그인은 시작할 때 모두 검사하고, 틀리면 서버가 시작하지 않는다 |
| `PluginState` (Entity) | 플러그인 하나의 켜짐·허락한 확장 지점·설정 값. 켜기(그 순간의 `uses`를 허락), 끄기, 값 넣기(칸 규칙 검사, 비밀값은 바로 암호화)의 규칙을 지키고 `platform.plugin.changed` 이벤트를 남긴다 |
| `PluginRepository` | `platform.plugins` · `platform.plugin_settings` ↔ `PluginState` |
| `PluginService` | 켜기·끄기·설정 (주인만). 설치 마법사·관리 화면·명령줄이 모두 이것을 부른다 |
| `PluginQuery` · `PluginController` | `GET /plugins`(주인: 전부와 설정 칸, 방문자: 동작 중인 것만), `GET /plugins/<이름>/settings`(공개 설정). 매번 DB에서 읽는다 |
| `PluginRegistry` | 들어 있는 플러그인 목록과 지금 동작 중인 등록. `reload()`로 DB를 다시 읽어 재시작 없이 다시 등록한다. 한 플러그인이 실패해도 나머지는 돈다(`problem()`) |
| `SecretBox` | 비밀값을 서버 키(`CAIRN_SECRET_KEY`)로 AES-256-GCM 암호화. 화면에는 "설정됨"만 |

**설정은 DB에**: 켜기와 설정은 설치 마법사·관리 화면(플러그인 메뉴)·`pnpm plugin`에서 하고 DB에 남긴다. `.env`에는 서버 키 같은 인프라만 둔다. 바뀌면 `platform.plugin.changed` 이벤트로 일꾼이 다시 등록한다. 새 버전이 확장 지점을 더 쓰면 다시 허락받기 전까지 동작하지 않는다.

**웹**: `<Slot name="post.after" context={…} />`가 화면 자리다. 웹이 시작할 때 `scripts/sync-plugins.mjs`가 들어 있는 플러그인의 화면 파일을 `apps/web/app/_plugins/installed/`로 복사하고 자리 목록(`slots.generated.ts`)을 만든다. 그릴 때 서버에 공개 설정을 물어 켜진 것만 그리므로, 켜고 끌 때 웹을 다시 빌드하지 않는다. 자리를 늘릴 때는 `WEB_SLOTS`, `<Slot>`의 context, 이 문서를 함께 고친다.

**서버 코드**: 목록 파일의 `server`(예: `server/plugin.ts`)가 `BasePlugin`을 상속한 클래스를 default로 내보내고, `register(cairn)`에서만 확장 지점에 등록한다. `PluginContext`는 목록 파일 `uses`에 적은 것만 열어 준다.

| 확장 지점 | `uses` | 등록 |
|---|---|---|
| 설정 | (목록 파일 `settings`) | `cairn.settings()` — 자기 설정만, 비밀값은 풀어서, 비어 있으면 기본값 |
| 웹 화면 자리 | (목록 파일 `web`) | 자리 `post.after`, `task.office` |
| 이벤트 받기 | `event:<무늬>` (예: `event:blog.post.*`) | `cairn.onEvent(무늬, new XxxHandler())`. 기능 패키지는 처리기 대신 쓰기 동작(`Command`, `allow = Operation.SYSTEM`)을 넘긴다: 코어(일꾼)가 서버 자신으로 트랜잭션 하나에서 돌리고 남긴 이벤트를 같은 outbox로 낸다 |
| 반복 작업 | `job:<이름>` | `cairn.every('5m', new XxxJob())` |
| 관리 동작 | `action:<이름>` | `cairn.addAction(이름, new XxxAction())` — 관리 화면(플러그인 메뉴)이나 `pnpm plugin <플러그인> <동작>`으로 부른다 |
| 보관 형식 복원 | `archive:restore` | 빈 Cairn에 들여온다 (`sync-github`) |
| 보관 형식 읽기 | `archive:read` | `cairn.archiveReader()` — vault 비공개 내용 포함 ([보관 형식](보관형식.md)) |
| 로그인 방법 | `login:<이름>` (예: `login:github`) | `cairn.addLogin(이름, new XxxLogin())` — `BaseLogin`(`start`: 보낼 주소, `finish`: 누구인지). 경로(`/api/auth/login/<이름>/…`)·확인값·로그인 쿠키·주인인지 판단은 코어가 하고, 주인이 연결해 둔 계정(`account.login_links`)으로만 로그인된다 |

**기능 패키지**: 코어를 고치지 않고 자기 표 · API · MCP 도구 · 콘솔 메뉴를 갖는 플러그인. 예: `plugins/browser-tabs`(서버 브라우저로 하는 일, [브라우저](브라우저.md)).

```
plugins/<이름>/
  cairn-plugin.json     schema · api · tools · menu, 그리고 uses(table · api · tool:<이름> · menu)
  migrations/           자기 스키마에만 (dbmate. 배포의 migrate가 코어와 함께 적용)
  server/plugin.ts      BasePlugin: cairn.addOperation(new XxxRead()) …
  server/operations.ts  동작 (Read · Command): 권한(allow) · 입력(input) · 일(run)
  server/views.ts       내보내는 모양 (콘솔 camelCase, MCP snake_case)
  server/tables.ts · schema.ts   pnpm db:rows가 자기 스키마에서 만든다 (행 타입 · 표)
  web/<화면>.tsx         콘솔 화면 (목록 파일 menu.page)
```

| 확장 지점 | 목록 파일 | `uses` | 코어가 하는 일 |
|---|---|---|---|
| 자기 표 | `schema`, `migrations/` | `table` | 배포 때 migrate가 적용. 동작의 `Work`는 자기 스키마의 표만 받는다(다른 스키마면 실행 전에 막음). `work.sql`도 자기 스키마만(`pnpm check`). 코어 표에 외래키 없음 |
| API | `api` (`"GET /reads": "list"`) | `api` | `/api/p/<이름>/reads`를 `PackageController`가 받아 동작을 찾는다. 경로의 `:id` · 주소의 `?값` · 본문이 입력이 된다 |
| MCP 도구 | `tools` (이름 → 동작 · 설명 · 입력 모양) | `tool:<이름>` | 요청마다 지금 동작 중인 패키지의 도구를 더한다 (`McpToolbox.toolsNow`). 주인만인 동작은 기기 · 에이전트에게 보이지 않는다 |
| 콘솔 메뉴 | `menu` (그룹 · 이름 · 아이콘 · 화면) | `menu` | 웹이 시작할 때 `packages.generated.ts`를 만들고, 콘솔은 동작 중인 패키지만 메뉴에 둔다. 화면은 `/admin/p/<이름>`이고 서버 호출(`call`)과 알림(`notify`)을 받는다 |
| 일 맡기기 | — | `task:request` | 동작이 `work.record`로 `task.task.requested`를 남길 수 있다 (에이전트에게 작업을 맡김. 결재는 그대로 주인에게) |

- **동작** (`platform/base/operation.ts`): `Read` · `Command`가 `Operation`을 상속한다. 순서는 코어(`PackageService`) 한 곳에서 지킨다: 권한(`allow`: 주인 · 누구나 · Actor 권한) → 입력(`input`, 틀린 칸을 모아 400) → 일(`run`, `Command`는 트랜잭션 하나, `work.record`의 이벤트는 같은 트랜잭션의 outbox로) → View. 입구(REST · MCP)를 모른다.
- **이벤트로 도는 동작**: `cairn.onEvent(무늬, new XxxCommand())`. `allow`는 `Operation.SYSTEM`이라 REST · MCP로는 누구도 부르지 못한다. 입력은 이벤트의 내용 + `spaceId`. 예: `browser-tabs`는 `task.approval.granted`를 받아 자기 결재 동작(`browser.site.publish`)이면 결과(`approvalId`, `outcome: done`)를 남겨 작업을 끝낸다 (서버는 발행하지 않고 주인이 직접 한다).
- **패키지의 이벤트**: 이름은 `plugin.<스키마>.<무엇>` (첫 칸에 밑줄을 쓸 수 없어서). 코어의 이벤트는 그 확장 지점을 허락받았을 때만 남긴다 (`task:request` → `task.task.requested`). 그 밖은 `work.record`가 실행 중에 막는다 (`PluginManifest.emits`).
- **표 읽기 · 쓰기**: 코어의 조건 규칙(`work.rows` · `row` · `exists` · `insertRows` · `updateRows` · `deleteRows` · `pageOf`). 그 기능만의 쿼리는 `work.sql`.
- **켜고 끄기**: 서버를 다시 시작하지 않는다. 꺼지면 경로는 404, 도구는 목록에서 빠진다. 새 패키지 폴더를 넣거나 마이그레이션이 바뀌면 배포(migrate · 재시작)가 필요하다.
- **이름과 표**: Drizzle 칸은 `plugin-api`의 `TableColumns`로 만든다 (생성된 `schema.ts`. 가져오는 범위는 아래 **경계**). 패키지 이름은 코어 스키마 이름(`platform` · `account` …)을 쓸 수 없다.

**운영 이미지**: 플러그인 서버 코드는 서버와 함께 tsc로 컴파일되어 `.ts` 옆에 `.js`로 놓인다. 코어는 확장자 없이 불러와 개발에서는 `.ts`, 운영에서는 `.js`를 읽는다.

**플러그인 API**: 플러그인 서버 코드는 `apps/server/src/plugin-api.ts` 한 곳에서만 가져온다 (기반 클래스, Actor, 오류, 이벤트, 보관 파일, `BaseLogin`·`LoginIdentity`).

**경계**: 플러그인은 자기 폴더 안의 파일, 화면에서는 `react`, 서버에서는 `node:*`와 `plugin-api`만 가져온다. 그 밖의 코어 파일을 가져오면 `pnpm check`가 막는다.

## 13. 작업과 결재

에이전트가 일하고 주인이 결재하는 구조. API는 [API설계.md](API설계.md), 표는 [테이블설계.md](테이블설계.md) 6장.

| 패턴 | 적용 위치 | 하는 일 |
|---|---|---|
| 상태 기계 | `Task`, `Approval` 엔티티 | 허용된 상태 변경만 메서드로 받고, 나머지는 `RuleViolation` |
| 임대 큐 | `next_jobs` | 러너가 일을 가져간다 (`FOR UPDATE SKIP LOCKED`). 러너가 죽으면 임대가 끝나 돌아온다. 들어오는 포트가 필요 없다 |
| 승인 게이트 + 명령 객체 | `Approval` | 위험한 동작을 대상·판 번호와 함께 저장만 하고, 승인 후 실행한다 |
| 사가 | 결재 → 실행 → 완료 | 모듈을 직접 부르지 않고 이벤트로 잇는다 |
| 추가 전용 로그 | `task.task_events` | 실행 기록, 보드, 오피스, 사용량이 같은 로그를 읽는다 |
| 전략 | 러너의 AI 실행 | `AiTool`(ClaudeCli · CodexCli)로 바꿔 끼운다 (구현이 둘이라 둔 약속) |

**결재 흐름** (글 공개의 예)

1. 에이전트가 초안을 저장하고 `request_approval`로 동작·대상·판 번호를 올린다. 에이전트의 요청은 작업 토큰의 `AgentActor`로 들어온다.
2. 결재 화면은 AI의 요약이 아니라 **서버가 대상에서 읽은 실제 내용**을 보여 준다.
3. 주인이 승인하면 `Approval.approve()`가 `task.approval.granted` 이벤트를 남긴다.
4. blog의 Handler가 이벤트를 받아 판 번호를 확인하고 공개한다. 승인자는 `ApprovedActor`로 넘어가고 `Post`의 주인 규칙이 이것도 받는다. 승인 뒤 내용이 바뀌었으면 실패로 처리한다. 같은 이벤트가 두 번 와도 결과가 같다.
5. 실행한 모듈이 결과 이벤트에 `approvalId`와 `outcome`(`done` · `failed`, 실패면 `error`)을 실으면 task가 받아 작업을 끝낸다. task는 어느 모듈이 실행하는지 몰라서 주제를 묻지 않고 내용만 본다 (`ApprovalResultHandler`는 `*`로 받는다). 주인이 거절하면 작업은 취소되고, 고쳐 달라고 하면 그 말과 함께 대기열로 돌아간다.

**일 요청**: 어느 모듈이든 `task.task.requested` 이벤트로 일을 요청한다 (세션 저장 뒤 vault가 정리를 요청, 기본은 꺼짐). 종류마다 필요한 권한은 `Task.SCOPES`에 있다: `tidy_session`은 `tidy`와 `read_all`이 함께 있는 에이전트만, `browse`(서버 브라우저로 하는 작업)는 `browse` 권한이 있는 에이전트만 맡고 `next_jobs`에서 `browser: true`를 알린 러너에게만 간다. `browse`와 `read_all`은 한 에이전트에게 함께 줄 수 없다 (로그인된 브라우저를 쓰는 에이전트는 비공개를 읽지 않는다). `code`(코드 작업)는 `code` 권한이 있는 에이전트만 맡고 코드 러너 칸 기기(기기 권한 `sandbox`, `Actor.inSandbox`)에게만 가며, 칸은 code만 받는다 (`Task.SANDBOXED`). `code`도 `read_all` · `write`와 함께 줄 수 없다 ([코드 작업](코드작업.md)). 러너는 `kind`로 스킬을 고른다: `draft_post`는 `cairn-write`, `tidy_session`은 `cairn-tidy`. 콘솔에서 지시만 준 일의 종류는 `general`이고 스킬 없이 지시대로 한다. 담당을 정하지 않은 일은 빌릴 때 가장 먼저 만든, 일을 받을 수 있는 에이전트가 맡는다.

**한도**: `report_progress`의 토큰을 에이전트의 한 달 한도에 더한다. 넘기면 에이전트가 멈추고 서버가 `task.agent.raise_limit` 결재를 올린다. 승인하면 한도가 두 배가 되고 다시 움직인다. 5시간 토큰 한도와 구독 사용률 멈춤은 다르다: 닿으면 새 일만 빌려 주지 않고 도는 작업은 끝까지 간다. 결재도 상태 변경도 없고, 창이 지나면 저절로 다시 일한다 (`Agent.holds`, 쉬는지는 저장하지 않고 계산). 초기화 시각이 지난 사용률은 쓰지 않는다.

**조직도와 목표**: 에이전트마다 보고 대상(`reportsTo`)을 둔다. 없으면 주인에게 보고한다. `Agent.reportTo(managerId, org)`가 순환(자기 자신·자기 팀원)과 깊이 4를 막고, 바꾸는 쪽은 공간의 에이전트를 모두 같은 순서로 잠근다 (동시에 서로에게 보고하게 바꿔도 순환이 생기지 않게). 결재는 조직도와 상관없이 늘 주인에게 온다. 목표(`goal/`, `Goal`)는 나무다: 맨 위가 회사 목표이고, 부모는 만들 때 정하고 바꾸지 않는다. 지우지 않고 `done` · `dropped`로 닫으며, 진행 중인 목표에만 작업과 하위 목표를 더한다. 작업은 만들 때 목표 하나에 이어지고(`goalId`), 상세는 회사 목표부터의 사슬을 보여 준다. 목표를 정하는 건 주인만이고 AI는 읽기만 한다.

**위임**: 팀장 에이전트는 작업 토큰으로 `delegate_task`를 불러 바로 아래 팀원에게 하위 작업을 맡긴다. 코드가 막는 것: 받는 쪽(바로 아래만), 종류(받는 에이전트의 권한으로 할 수 있는 것만, `Task.delegableWith`), 한도(한 번에 5개 · 작업 하나에 10개 · 깊이 3 · 라운드 3, `Task.assertCanDelegate`). AI가 정하는 것: 무엇을 나눠 누구에게, 지시를 어떻게, 결과가 충분한지. 새 상태는 없다: 맡긴 작업은 `waiting`에 `subtasks`를 적고(`Task.waitForSubtasks`), 러너는 결재 대기처럼 AI를 끄고 제출하지 않는다. 하위 작업이 끝날 때마다 `SubtaskSettledHandler`(`task.task.changed`)가 위 작업만 잠그고 남은 하위 작업을 세어, 없으면 대기열로 돌린다(`Task.wakeAfterSubtasks`). 둘이 동시에 끝나도 늦게 커밋한 쪽이 깨운다. 다시 빌려 간 일에는 하위 작업의 결과가 실린다. 위 작업을 취소하면 아래 작업도 함께 취소된다 (위 → 아래 순서로 잠근다). 결재는 누가 올리든 주인에게 온다.

**하트비트**: 에이전트마다 정해진 시각에 깨운다 (`heartbeat/`, `Heartbeat`). 주기는 매일(시각 + 요일)과 N시간마다 둘뿐이고, 시각은 `HeartbeatPolicy`가 시간대(IANA)의 오프셋을 Intl로 구해 계산한다. 크론 라이브러리는 넣지 않았다. 일꾼의 `HeartbeatJob`이 1분마다 때가 된 하트비트를 `SKIP LOCKED`로 잠가 다음 시각으로 넘기고(`Heartbeat.fire`, 놓친 시각은 한 번만), 에이전트가 일을 받을 수 있고 앞 하트비트 작업이 끝났을 때만 "정기 확인" 작업을 만든다. 작업의 `request_id`가 `heartbeat:<에이전트>:<시각>`이라 두 번 돌아도 하나다. 팀장의 하트비트 작업은 위임으로 팀에게 일을 나눈다.

**러너**: `apps/runner`는 서버 모듈이 아닌 별도 프로그램이다. MCP로만 서버와 이야기하고 DB에 닿지 않는다. 작업마다 빈 폴더와 별도 설정으로 AI CLI를 띄우고, 실행 로그를 읽어 `report_progress`로 보낸다.

- **격리**: 설정·홈은 빈 임시 폴더, MCP는 cairn 하나만, claude.ai 연결은 끈다. 다른 MCP 서버가 보이면 바로 끄고 `failed`로 끝낸다. 기기 토큰은 AI CLI에게 주지 않고, 작업 토큰은 작업 폴더 밖의 `mcp.json`에만 쓴다.
- **권한**: 셸을 주지 않는다. 내장 도구는 Read·Write·Edit과 스킬, MCP는 cairn만. 예외는 샌드박스 컨테이너인 코드 러너 칸의 code 작업뿐이다 ([코드 작업](코드작업.md), 셸은 3단계). 작업 폴더 밖 읽기는 `-p`에서 물을 사람이 없어 거절되지만, 권한 설정이 바뀌어도 막히게 주인의 홈을 `settings.json`의 deny로 적어 둔다 (2026-11-01 실제 CLI로 확인).
- **끝내기**: 서버의 답으로 정한다. `cancelled`와 `waiting`이면 끄고 제출하지 않는다. `paused`면 끄고 돌려준다. 끝난 코드가 0이어도 결과가 오류면 `failed`다.
- **토큰 계산**: 입력 + 캐시 생성 + 출력. 캐시 읽기는 빼고 한도에 넣는다.
- **서버 러너**: 서버와 함께 뜨고 스스로 연결한다 (개발 compose에도 있다). 서버가 시작할 때 서버 키에서 만든 연결 값(`ServerRunnerPolicy`)을 서버와 러너만 붙는 볼륨에 쓰고(`ServerRunnerGateway`), 러너는 그 값을 `POST /api/devices/server-runner`에 내밀어 "서버 러너" 기기의 토큰을 받아 메모리에만 둔다. 서버 러너 기기는 공간마다 하나고, 다시 연결할 때마다 토큰을 바꿔 앞 토큰을 막는다. 주인이 끊어도 러너는 거절(401)을 받으면 다시 연결한다: 쉬게 하려면 끊지 않고 일 받기를 끈다. 사람이 토큰을 옮기지 않고, 토큰은 디스크에 남지 않으며, 설치 전에 떠도 설치가 끝나면 붙는다. root가 아닌 사용자, 읽기 전용 루트, 메모리 `/tmp`와 홈, 권한 없음, 받는 포트 없음, 볼륨은 연결 값을 읽기만.
- **코드 러너 칸**: 서버 러너와 같은 길로 스스로 붙되 연결 값 · 입구 · 볼륨이 따로다 (`ServerRunnerPolicy.codeSecret`, `POST /api/devices/code-runner { secret, slot }`, `CAIRN_CODE_PAIRING_FILE`). 칸마다 기기 하나(`코드 러너 <칸>`, 권한 `run` · `sandbox`). 칸 번호(`CAIRN_RUNNER_SLOT`)는 코드 러너 이미지(`CAIRN_SANDBOX=1`)에서만 받는다. 칸인지는 서버가 기기로 정하고 `next_jobs`에는 싣지 않는다. 작업 공간(clone · 셸)은 3단계라 지금 칸은 code 일을 AI 없이 실패로 끝낸다. 구성 · 단계는 [코드 작업](코드작업.md).
- **러너 메뉴**: 러너가 서버에 닿을 때마다(`next_jobs` · `report_progress` · `ai_login`) `task.runners`에 닿은 때를 남긴다 (version 없이, `RunnerRepository.seen`). 주인은 러너 메뉴에서 연결 상태와 지금 하는 일을 보고 일 받기를 켜고 끈다(`Runner.setAccepting`). 끄면 서버가 일을 주지 않을 뿐 러너 프로세스는 켜진 채로 쉰다: 웹은 컨테이너를 켜고 끄지 않는다. 기기 이름·종류는 account의 것이라 화면이 기기 목록과 `deviceId`로 합친다. 서버 키와 DB 주소를 주지 않는다. Claude 토큰은 콘솔에 넣고 일마다 `ai_login`으로 받아 메모리에만 둔다. 러너 `.env`에 토큰이 있으면 그것이 먼저다.
- **웹 AI 로그인**: 주인이 AI 메뉴에서 로그인을 누르면 서버는 `ai_signin` 작업만 만들고(에이전트 없음, 도구마다 하나), 러너가 로그인 명령을 `script`로 만든 PTY에서 돌린다 (Ink 화면이라 TTY가 있어야 한다. 러너 이미지에 python3가 없어 util-linux의 `script`를 쓴다). 빈 설정 폴더, 다른 인증 환경 변수는 비우고, `BROWSER=true`로 브라우저를 열지 않게 한다. 화면은 비밀로 다루어 기록하지 않고, 정해진 모양의 주소·코드·자격만 `ai_signin`으로 보낸다. 서버는 받은 값을 `AiSigninPolicy`로 한 번 더 걸러 `ai_logins`에 잠가 저장한다. 2초마다 `ai_signin`으로 코드와 취소를 묻고, Claude 코드는 쳐 넣은 뒤 Enter를 150ms 뒤에 따로 친다(함께 보내면 붙여 넣기로 읽혀 제출되지 않는다). 한 번에 하나, 5분이 지나면 실패. 리눅스에서는 `timeout`으로 감싸 러너가 갑자기 죽어도 로그인 명령이 5분 반 뒤에 끝나고, 러너가 시작할 때 10분 넘게 남은 로그인 폴더를 지운다(`SigninRun.sweep`). Claude 토큰은 표시 문구 사이에서 찾고, 문구가 바뀌어도 명령이 잘 끝났으면 화면의 마지막 토큰을 쓴다(한 번만 보여 주는 토큰을 잃지 않게). 실패 이유는 화면의 글 대신 단계별로 정해진 문구다. Paperclip의 같은 기능(MIT)에서 화면 읽기 규칙을 가져왔다 (`SigninScreen`, `SigninTerminal`, `SigninRun`).
- **AI 도구 어댑터**: 일은 도구와 상관없이 같은 순서로 돈다 (`JobRun`: 자리 만들기 → 띄우기 → 출력 읽기 → 바뀐 자격 되돌려 쓰기 → 끝 알리기). 도구마다 다른 것(설정 파일, MCP를 붙이는 법, 셸을 막는 법, 출력 모양, 자격 모양)만 `AiTool`(`ClaudeCli` · `CodexCli`)과 `AiStream`(`ClaudeStream` · `CodexStream`)에 둔다. 각 회사의 공식 CLI를 고치지 않고 그 회사의 구독 로그인으로 띄운다: Anthropic은 고치지 않은 Claude Code 바이너리만 구독 로그인을 허락한다(Agent SDK를 거치는 acpx의 Claude 다리는 API 키 대상).
- **Codex**: 공식 `codex exec --json`. 작업마다 새 `CODEX_HOME`(config.toml + auth.json), 셸을 끄고(`features.shell_tool` · `unified_exec`) 작업 폴더만 쓰는 sandbox(네트워크 없음), `--strict-config`로 설정 이름이 바뀐 버전은 시작부터 실패한다. sandbox는 읽기를 막지 않아(실험으로 확인) 셸을 끄는 것이 첫 벽이다. MCP는 cairn 하나, 작업 토큰은 환경 변수(`CAIRN_RUN_TOKEN`)로만. 셸이 없어 SKILL.md를 스스로 읽지 못해 스킬은 지시문에 넣는다. 갱신 토큰이 쓸 때마다 바뀌므로 끝난 뒤(취소 · 실패여도) 바뀐 auth.json을 `ai_login_refresh`로 되돌려 쓰고, 서버는 Codex 일을 한 번에 하나만 빌려 준다. 셸 명령 · 다른 MCP 서버가 보이면 끄고 실패로 끝낸다. 토큰은 턴이 끝날 때 한 번 오고(캐시 읽기 빼고 셈), 구독 사용률은 exec가 알려 주지 않아 아직 읽지 않는다.
- **할 수 있는 것 알리기**: 러너는 시작할 때 설치된 AI CLI와 PTY를 보고(`RunnerAbility`), `next_jobs`에 일할 수 있는 도구 · 웹 로그인을 돌릴 수 있는 도구 · 스스로 가진 로그인을 싣는다. 쓸 로그인이 있는지는 서버가 알아서(`LeasePolicy`) 로그인이 없는 도구의 일은 빌려 주지 않는다: 빌렸다 돌려주면 실행 기록이 쌓이기 때문이다. 콘솔에서 로그인하면 서버의 긴 폴링이 5초 안에 다시 살펴 재시작 없이 이어 간다. 그사이 만료되면 일마다 받는 `ai_login`이 거절하고 러너는 일을 돌려준다. CLI를 새로 깔면 러너를 다시 켠다.
- **서버 브라우저** (`browser-tabs` 패키지): `CAIRN_BROWSER_URL`(CDP 주소)이 있으면 탭 읽기(`TabReader`, 일과 따로 돎)를 하고, 서버 러너면 `next_jobs`에 `browser: true`를 알려 브라우저 작업(`browse`)도 받는다. 그 작업에만 AI CLI에 Playwright MCP(`BrowserMcp`)를 붙이고 격리 검사가 `playwright`를 허락한다. 브라우저에 닿지 못하면 실패가 아니라 돌려주고 기다린다. 구조 · 흐름 · 안전장치는 [브라우저](브라우저.md).
- **멈추기**: 첫 신호는 기다리는 `next_jobs`가 끝나기를 기다린다. 끊어도 서버는 시간이 다 될 때까지 찾다가 없는 러너에게 일을 빌려 주기 때문이다 (그 일은 임대가 끝나는 15분 뒤 돌아온다). 두 번째 신호는 바로 끊는다.
